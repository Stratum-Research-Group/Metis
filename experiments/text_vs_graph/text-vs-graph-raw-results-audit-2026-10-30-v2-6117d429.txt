2026-10-30 (supplements the same-day report review; replaces v1)

SCOPE
Audited the supplied results JSONL: 10,800 rows, one per scored final
answer, fields: story_id, qid, qtype, arm, level, pass1_raw, raw, parsed,
gold, correct, parse_ok, tokens_in, tokens_out, seconds, seed, exposed.
This is raw-row verification of the report's numbers. The frozen manifest,
prompts, corruption log, request/decoder settings (including output caps
and finish reasons), code revision and model artifact were NOT supplied,
so provenance, freeze, exposure-label and cap claims remain unverified.
No code was changed and no inference was run.

NEW OBSERVATIONS FROM THE RAW ROWS

N1. Parse failures are strongly consistent with output-length truncation.
   99.2% of parse failures have tokens_out >= 448 (vs 9.2% of parsed
   rows). The maximum observed tokens_out for arms A, B, C is exactly
   512, with 568 rows sitting at exactly 512 (A 153, B 173, C 242), and
   failure raw tails end mid-sentence. Example, row conf_s001_q3, arm C,
   level 0.3, tokens_out 512, raw ends:
     '...Text: "Event E8 requires parent events (E2, E5) under rule AND"
      Structured Facts: "DEPENDENCY: E8 requires (E7) with rule'
   This pattern strongly suggests an output-token limit near 512 for
   these arms, but finish_reason and request caps were not supplied, so
   it is not proven. 78.3% of all parse failures are Q3 (the dependency-
   closure question); Q3 also contributes 77.4% of all 840 errors.
   Rare other failure modes exist: 4 rows are a bare template artifact
   (row conf_s002_q2, arm C, level 0: raw is exactly
   '<|channel>thought<tool_call|>', tokens_out 4), and some D pass-1
   outputs degenerate into repetition loops (row conf_s004_q1 pass1_raw
   ends '_de_de_de_de_...', tokens_out 762).
   Caution: these rows alone do not show how much of the arm differences
   is attributable to output budget versus reasoning; that would need
   the request settings and, ideally, a preregistered sensitivity
   analysis. Do not present the budget explanation as established.

N2. D and F reach a maximum tokens_out of exactly 762, versus 512 for
   A, B, C. The rows cannot distinguish two explanations: a higher
   output cap for the two-pass arms, or tokens_out summing both passes
   of the two-pass design (which the plan may intend). If it is a sum,
   the larger per-question token totals for D/F are by design, not a
   protocol defect - but then cross-regime token/latency comparisons
   (D/F vs A/B/C) mix a two-pass cost structure with single-pass costs
   and must be labeled as such. H4's D-versus-F comparison is not shown
   to be cap-equal either: equal observed maxima do not prove equal
   answer-pass caps. Disclosure needed: per-arm output caps, whether
   D/F token fields include pass 1, and pass-1/pass-2 split. No rerun
   recommendation is made here; any cap-sensitivity check would be a
   new, outcome-selected exploratory analysis, not a replacement or
   completed confirmatory comparison.

N3. Exposed-only breakdown (conditional on the exposed flag).
   At 30% corruption, 627 of 1,200 questions per arm carry exposed=true,
   with an identical exposure set across arms (pairing holds). Accuracy
   on exposed=false questions is 96.2-99.5% in every arm; on
   exposed=true questions: B 53.4%, C 77.7%, D 88.7%, F 94.4%. Paired
   story-level exposed-only contrast C30-B30: +21.9 points
   [+16.9, +26.8] (my bootstrap, same method as item 6).
   Caveat: the exposed flag itself was not validated against a corruption
   log, so these breakdowns are only as good as that labeling. If the
   flag is accurate, the pattern is consistent with the intended
   protection mechanism; that is a statement about consistency, not
   established causation.

N4. D's flag pass: observable behavior, not detection performance.
   At level 0 (nothing to flag), 230 of 1,200 D pass-1 outputs contain
   no JSON array: mostly benign prose equivalents of 'no issues', plus
   some repetition loops (N1). 29 of 1,200 (2.4%) flagged at least one
   item at zero corruption. At 30%, D produced at least one flag in 736
   of 1,200 question passes, and 625 of 627 exposed questions (99.5%)
   had at least one flag. That 99.5% is an any-flag rate per question,
   NOT detection recall: true precision/recall requires matching flags
   to the actual corrupted facts, which needs the corruption log (not
   supplied). Question-level matching also overcounts false positives,
   since a correct flag on a story appears on that story's unaffected
   questions too.

N5. Question-type profile (fills part of review finding 6).
   Level 0 accuracy: Q1 99.7%, Q2 97.6%, Q3 86.7%, Q4 99.5%.
   Level 0.3: Q1 97.1%, Q2 93.7%, Q3 62.5%, Q4 97.3%.
   Q3 (dependency closure, long-form list answers) carries most of the
   errors and most of the truncations. Claims about the benchmark are
   mostly claims about Q3; the report should say so.

BOTTOM LINE
Every report figure directly entailed by result rows checks out exactly:
condition counts, deltas, parse rate, scoring consistency. Call totals
are inferred from non-empty pass1_raw fields, not an execution log, and
the CIs reproduce approximately, within bootstrap noise - both noted.
No arithmetic or scoring contradiction exists. The main open scientific
caveats: parse failures look like output-length truncations concentrated
in Q3 (settings not supplied, so not proven), and the token accounting
for two-pass arms needs disclosure before cross-regime cost comparisons
are interpretable. Next artifacts needed: the corruption log (for N4
precision and finding 6) and the frozen manifest plus request/decoder
settings (findings 5, N1, N2).
