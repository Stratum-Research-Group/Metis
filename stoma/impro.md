# Stoma improvement and benchmark plan

Review date: 2026-09-29. Reviewed working tree at `168e2f9` plus uncommitted Round 4 changes. This is a plan, not a claim that the proposed fixes or benchmarks have run. Preserve the current local only runtime, pinned submodules, single facet encoder contract, provenance validation, and zero edge Dianoia limitation while changing Stoma owned code.

## Executive assessment

Stoma has unusually careful tests for parser failures, provenance, crash recovery, and source lifecycle. Its main gap is that it has **no Stoma benchmark or measured retrieval quality target**. The acceptance report records an older 72 test run and one peak RSS value, but cannot establish current throughput, query latency, scale, retrieval relevance, or cost per edit. The LTHCM submodule has its own benchmarks; those results do not measure Stoma's parsing, chunking, metadata, persistence, or command path.

The biggest architectural cost is whole index work on small changes. A fresh file copies the serving engine and manifest; an edit, move, or deletion rebuilds the engine from source files; every commit serializes another complete generation. This makes repeated ingestion and storage growth likely to dominate at scale. Measure this before optimizing it.

### Order of work

1. **Establish measurements:** land benchmark fixtures and harness, capture the unmodified baseline, and record current test results. This prevents optimizing the wrong component.
2. **Close correctness holes:** sync error handling, writer coordination, CLI argument/timestamp fidelity, and truthful reconciliation summaries.
3. **Cut write amplification:** batch initial ingest into one transaction, then replace whole corpus rebuild with safe incremental storage. Recheck all existing provenance, causal, rollback, and dual store tests.
4. **Make scale sustainable:** checkpoint startup validation, generation retention, bounded storage, and a trusted serialization boundary.
5. **Improve retrieval quality from evidence:** tune chunking and retrieval only after a labeled evaluation shows which query types fail.

## Benchmark specification

Build a Stoma specific harness; do not relabel LTHCM submodule scores as Stoma results. Compare four paths on the **same parsed passages and labels**: lexical BM25, cosine similarity with Stoma's exact encoder, current Stoma/LTHCM retrieval, and a simple reciprocal rank fusion of lexical plus dense. Declare any baseline requiring an extra local package. Pin versions, corpus snapshots, model revision/checksum, chunk settings, query set, random seed, and scoring code. Do not use internet access during measured runs.

### Workloads

| Track | Fixture and measurement | Main question |
|---|---|---|
| Correctness smoke | Small mixed Markdown, PDF, code, OCR artifact, and transcript corpus; include edits, moves across roots, deletes, restart, corrupt generation, and future dated document. | Do results have correct content, locations, hashes, and causal status throughout lifecycle? |
| Retrieval quality | Frozen, redistributable or locally supplied corpus with source and passage relevance labels; include exact term, paraphrase, code symbol, metadata, long document, and negative queries. | Watcher | Burst create/modify/move/delete, queue overflow, retry exhaustion, and reconciliation on restart. | Time to convergence, lost event count, backlog, and false success count. |
| Crash/recovery | Kill writer before and after pointer publication, interrupted serialization, disk full or sync failure where testable, and corrupt active generation. | What data survives and how long does recovery take? |

### Metrics and protocol

- **Quality:** source Recall@1/5/10, passage nDCG@10, MRR@10, no answer false positive rate, provenance exact match rate, and causal violation count. Score missing/failed queries as failures. Report per format and query type, not only an overall average.
- **Speed:** cold startup, first query, warm query p50/p95/p99, files and MiB per second, chunks per second, single edit/delete/move latency, and watcher convergence. Time parsing, chunking, embedding, index mutation, commit, and recovery separately. Use monotonic clocks.
- **Resources:** process peak RSS in fresh subprocesses, CPU time, index bytes, manifest bytes, total generations bytes, bytes written per update, and model cache size separately. Compare memory at each corpus size; embedding batch memory is bounded but the engine and manifest currently scale with corpus size.
- **Reliability:** success, failure, indeterminate counts; dual store/manifest ID equality after every workload; source count; retained generations; and exact test fixture sizes. Never exclude failures from denominators.
- **Repeatability:** one untimed warmup where relevant, at least five measured runs for short workloads and three for expensive scale runs, fixed query order or recorded shuffle seed, median plus spread or confidence interval, machine/OS/CPU/RAM/storage details, revision and dirty tree state. Run baselines under identical hardware and cache policy. Save raw JSONL and a human readable summary outside Git unless fixtures/results are intentionally small and approved for tracking.

### Initial acceptance targets (proposals, not measured claims)

The first baseline determines realistic latency and throughput budgets. Set these hard correctness gates now: zero lost or duplicate passage IDs after lifecycle operations; 100% returned result provenance consistency; zero future document leakage when causality is enabled; zero ordinary success reports after acknowledged sync failure; and zero false reconciliation deletion successes. For quality, require Stoma to match or exceed same encoder cosine retrieval on source Recall@10 within a predeclared tolerance, then justify any added latency. Publish negative results. For performance, target at least a 10x reduction in single file update work at 10,000 files after incremental storage, while reporting the actual achieved factor and confidence interval.

### Reporting template for each run

Record: revision and dirty status; command; Python/package/model identities; dataset IDs, licenses, hashes, bytes, file/page/chunk/query counts; machine and storage; cold/warm policy; raw metric file path; median/spread; failures and exclusions; baseline comparison; and limitations. A test suite passing is a correctness signal, not a retrieval benchmark. Any unavailable large workload must be marked **not run** with its reason rather than replaced with a small fixture and labeled as scale proof.
