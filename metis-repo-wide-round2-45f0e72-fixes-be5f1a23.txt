ITEM 1. P0 - LAN MODE REJECTS REAL LAN HOSTS [REPRODUCED]
Where: prosopon/prosopon/server.py:111-120 (allowed_hosts and _validate_host_header),
called first by require_auth (line 122), pair_device (line 215) and generate_pin.
Observed: with host=0.0.0.0, allowed_hosts is loopback plus "0.0.0.0". A phone at
http://192.168.1.50:8000 sends that Host header. POST /api/auth/pair returned 403
for Host 192.168.1.50 and for Host metis.local. So advertised phone pairing and
every authenticated route fail in LAN mode. Tests pass only because they use
the "testserver" host.
Fix: build the allow-list from explicit config (new setting, e.g. allowed_hosts,
default loopback names). In LAN mode require the owner to list the LAN IP or
hostname, or derive from the machine's actual interface addresses at startup and
log them. Reject everything else with 403. Never allow "0.0.0.0" as a Host value.
Also remove "testclient", "testserver" and "test" from the production allow-lists
(server.py:111, :125, :170, :203) and let tests inject them through config.
Test: LAN config with allowed host 192.168.1.50: pair and sessions succeed with
that Host; a different Host gets 403; a spoofed Host:evil.example gets 403 even
from a paired token; "testclient" as client host is not treated as loopback.

ITEM 2. P0 - HESTIA CONTROL ROUTES HAVE NO AUTH, NO HOST CHECK, NO CONTENT-TYPE CHECK [REPRODUCED]
Where: hestia/src/hestia/api/app.py:348 (/manage/load), :371 (/manage/unload),
and the /v1 routes. App created at app.py:83-106 with no middleware.
Observed: an in-process test request to POST /manage/unload with Content-Type:
text/plain, Origin http://evil.example and Host evil.example:8080 returned 200 and
called unload (await request.json() ignores content type). This shows the server
accepts such a request. I did NOT test a real browser or real DNS rebinding;
browser protections (for example private-network-access checks) may block or

plus configured); (b) require Content-Type application/json on every POST and

/manage/*, /v1/chat/completions, /v1/embeddings and /models; (d) fail closed if
the token is unset unless an explicit dev flag is on, and print a loud warning;
(e) give run_stack.sh and the Kybernetes HestiaAdapter the token.
Test: no token = 401; wrong Host = 400/403; text/plain body = 415; cross-origin
Origin gets no CORS grant; the CLI manage commands still work with the token.

ITEM 3. P0 - KYBERNETES REPORTS "VERIFIED" FROM ONE SHARED WORD [REPRODUCED]
Where: kybernetes/kybernetes/adapters/krisis.py:114-206 (verify_response, final
return at :198); kybernetes/kybernetes/engine/pipeline.py:659-660 (tool output
becomes VERIFIED) and :443 (a denied approval is also finalised as VERIFIED).
Observed with one citation "The moon orbits the earth every month.":
  "The moon is made entirely of green cheese [1]."  -> status verified
  "The moon does orbit the earth [1]. The sky is purple." -> status verified
Support is "any non-stopword in common with the citation or its title". Sentences
with no marker are skipped. The report says is_simulated=True and
verifier_mode=heuristic, but status is still "verified" and the explanation says
"supported by N verified evidence citations". The final turn status is copied
from that field. Also any tool output (calculator or file_search) sets the turn
to VERIFIED without a verifier.
Fix: this adapter must never emit VERIFIED. Cap heuristic results at a new
status such as CITED_UNVERIFIED (or DRAFT) with the explanation "citations
present; no entailment check run". A real selector or NLI component is not
enough on its own to justify VERIFIED. Require named, actually executed checks
(for example per-claim support against the cited passage by a named verifier and
version, citations resolved, is_simulated=False) and word the status as "supported
by cited evidence under check X". Absence of a detected conflict is not truth and
must not be shown as verified. Calculator output may be VERIFIED only for
the arithmetic result; file_search output must not be. Denied approval should be
a typed DENIED status, not VERIFIED (pipeline.py:443). Make uncited sentences
count as unsupported when the response had citations available.
Test: the two sentences above must not return verified; a deterministic
calculator turn may; a denied approval has its own status; the Prosopon UI shows
the new status text.

ITEM 4. P0 - PAIDEIA PROMOTES UNVERIFIED WALKS TO GOLD AGAIN [REPRODUCED]
Where: paideia/paideia/contracts/dianoia_schema.py:36-44 (validate_verification_state);
source of the value: dianoia/dianoia/walk.py:882-889 (_verify_answer).
Observed: a record whose verification is only
{"conflicts_found": false, "report": "No evidence passages to verify against."}
validates with verified=True, provenance="dianoia_sheaf_verification" and
is_defensible_gold_trajectory() == True. Dianoia emits exactly that shape when it
has no evidence to check. The validator treats "conflicts_found is not None" as

verifier_mode of "none") when there are no passages and when no verifier ran,

named verifier_mode plus is_correct is True from an independent label, not just
absence of conflict. Keep unverified counts in the audit.
Test: the record above is excluded and counted as unverified_excluded; a record
with verified=True, mode sheaf, provenance set by the producer and is_correct=True
is kept; legacy records are excluded rather than relabelled.

ITEM 5. P1 - GPU LOCK DOES NOT GIVE MUTUAL EXCLUSION [REPRODUCED]
Where: paideia/paideia/training/hardware.py:120-136 (release_gpu_lock);
hestia/src/hestia/device_lock.py:43-53 (release) and :69-72 (acquire).
Three defects, all reproduced with temp lock directories:
 a. Paideia's runner calls release_gpu_lock() in a finally block even when its
    own acquire FAILED. That function unlinks /tmp/metis_gpu.lock regardless of
    ownership. With Hestia holding the lock, Paideia failed to acquire, released,
    and deleted Hestia's lock path. A second trainer then acquired a fresh file
    while Hestia still held the old one. Two holders.
 b. Hestia's GpuDeviceLease.release() unlinks the lock file after unlocking. A
    contender that already opened the old inode can lock it while a new caller
    creates and locks a new inode. Both held a lock at once.
 c. acquire_device_lease() releases any existing in-process lease for the same
    device and then hands out a new one, so a second ServerManager or code path in
    one process silently steals the lock. The second acquire returned a lease.
Fix: never unlink lock files; they are permanent. Release only unlocks and
closes the fd you own. Track ownership: release_gpu_lock does nothing if this
process did not acquire. Remove the "abandoned in-process lease" branch and
return None when the device is already leased in this process. Create the lock
directory with 0700 under a per-user path (XDG_RUNTIME_DIR or /run/user/UID) and
open with O_NOFOLLOW instead of world-writable /tmp.
Test: holder A, contender fails, contender "release" leaves A's lock intact; two
acquires in one process: second returns None; unlink race cannot produce two
holders; stale lock from a dead pid is reclaimed without deleting the file.

ITEM 16. P1 - TOOL BOUNDS ARE CHECKED AFTER THE FACT [SOURCE]
Where: kybernetes/kybernetes/tools/registry.py:105-115 (timeout compared after
execute returns); kybernetes/kybernetes/tools/file_search.py:154 (result-cap
return says truncated False) and the tool description promising regex.
