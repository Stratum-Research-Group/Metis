======================================================================
0. WHAT THIS IS AND IS NOT
======================================================================
Goal: let the owner (Nick) use MSS (chat, approvals, workbench, squad view) from another device - phone, laptop browser, second desktop - while MSS and its models keep running on his home machine. Plus a "Manage Devices" window and a Settings section to control who can reach MSS, how, and with what powers.

Not in scope: running MSS in the cloud, any MSS-required relay or account, telemetry, multi-user teams. MSS is local-first and single-owner. T3's "T3 Connect" depends on T3's hosted relay and a cloud sign-in; Pyle does not copy it.
External dependencies, stated plainly: the core paths (LAN, SSH forward, owner-run reverse proxy/self-hosted relay) need no third-party account or service. Tailscale is an OPTIONAL route: it needs a Tailscale account and Tailscale's coordination service and is outside MSS's control. MSS only detects and uses it if the owner already runs it; it is never required or bundled.

Not a defect report. Section 2 lists real weaknesses in today's pairing code because remote exposure makes them matter, but nothing here claims MSS is currently unsafe on a loopback-only setup.

1. WHAT T3 CODE DOES (REFERENCE, FROM DOC + SOURCE)
======================================================================
1.1 Ways to reach a host machine [T3]
- T3 Connect: cloud relay, no port forwarding, needs account sign-in. (Skip for MSS.)
- LAN / private network direct pairing: host binds to a private IP (t3 serve --host <ip>), user makes a one-time pairing link/QR, other device scans or pastes it.
- Tailscale HTTPS: tailscale serve mapping gives https://machine.tailnet.ts.net/ (t3 serve --tailscale-serve, t3 pair --tailscale).
- Desktop-managed SSH: desktop app starts/reuses a server on the remote host and forwards the port.
- Hosted web app needs an HTTPS endpoint; it connects direct to your server.

1.2 Multiple routes per machine [T3]
- One machine can have several routes (LAN, Tailscale, VPN, public URL, SSH). Pairing again over another address adds a route, not a second machine.
- Routes are ordered by speed, user can drag to reorder. First route that answers wins. Dead LAN routes are skipped briefly and retried last. Client re-checks earlier routes on network change, app focus and every minute, and moves back when one works.
- Server reports its current LAN/Tailscale addresses while connected, client adds them as "learned" routes (reorderable, not removable).
- Tailscale range 100.64.0.0/10 is shared with other VPNs, so it only shows as Tailscale if confirmed.

1.3 Auth model (source) [T3]
- Server auth policy descriptor with 4 values: desktop-managed-local, loopback-browser, remote-reachable, unsafe-no-auth. Chosen from bind host (remote-reachable if not loopback).
- Bootstrap methods: desktop-bootstrap or one-time-token.
- Session methods: browser session cookie (httpOnly, sameSite lax), bearer access token, DPoP-bound access token.
- Pairing link: one-time credential, default TTL 5 minutes, optional label, optional scope list, can be revoked before use. Consumed on use.
- Session: stored in auth_sessions with id, subject, role, method, issued/expiry, revoked_at, plus client metadata (label, IP, user agent, device type, OS, browser). Default TTL 30 days.
- Live state: lastConnectedAt and connected (websocket currently open) per session, plus "current" (this is the session making the request).
- Websocket tickets: short-lived (5 min) tickets instead of putting the long credential on the socket.
- Scopes (fine-grained): orchestration:read/operate, settings:write, providers:manage, environment:maintain, preview:operate, diagnostics:read, terminal:read/operate, filesystem:read/write, source-control:write, access:read/write, relay:read/write. A pairing link can be created with a narrower scope list. They note that terminal/agent operate already reaches full power, so narrowing means choosing explicit scopes.
- Access stream: server pushes snapshot + upsert/remove events for pairing links and client sessions so the devices list updates live.
- Revoke one session, revoke all other sessions, revoke a pairing link. "Revoke others" is disabled when there is nothing else.
- Headless CLI: t3 auth pairing create|list|revoke and t3 auth session issue|list|revoke <session-id>.
- A "Permissions" view shows what the current connection can do; it applies only to the route marked "In use".

1.4 UI (ConnectionsSettings.tsx) [T3]
Settings > Connections: network access toggle, pairing link creation (with QR + copy), list of active pairing links with Revoke, list of authorized clients with Revoke and "Revoke others", route list per machine with reorder/remove/Add route, Permissions, Load balancing across machines, Tailscale HTTPS toggle, Add environment (SSH). "Changing network access restarts the desktop app."

1.5 Parts of T3's design I am NOT carrying over
- T3 Connect cloud relay, account sign-in, push relay, mobile push (APNs/FCM), webhooks held while offline. Cloud dependency; conflicts with MSS being fully offline.
- Auto-balance of new threads across machines. MSS has one GPU host. Park until there are two hosts. [OPEN]
- Codex/ACP provider account management. Not relevant.

2. WHAT MSS ALREADY HAS (STARTING POINT)
======================================================================
2.1 Existing pairing and auth in Prosopon [EXISTS]
- prosopon serve --lan binds 0.0.0.0, prints a 6-digit pairing PIN valid 5 minutes. prosopon pair prints a new PIN. prosopon revoke revokes all device tokens.
- PairingManager (auth/pairing.py): PIN pairing, tokens are secrets.token_urlsafe(32), stored only as SHA-256 hash in data_dir/paired_tokens.json, expiry default 72h (session_expiry_hours), PIN record in pairing_pin.json. 5 failed PIN attempts triggers a 15 minute lockout. Cross-process sync via files.
- PairedDevice fields: token_hash, role ("chat" or "admin"), device_name, paired_at_utc, expires_at_utc, ip_address.
- Endpoints: POST /api/auth/pin, /api/auth/pair, /api/auth/local-token, /api/auth/revoke. Revoke by a non-admin token revokes only itself; admin token revokes ALL.
- require_auth: loopback callers are exempt when the server is not in LAN mode; otherwise bearer token required. require_admin_auth: no loopback exemption, admin role required (used for /api/dashboard/*, approvals, workbench).
- Host header allow-list, Origin check, Sec-Fetch-Site cross-site rejection, CSP, X-Frame-Options DENY.
- Optional self-signed TLS (prosopon serve --tls) with generate_self_signed_cert.
- Web UI: a "Device Pairing" PIN modal (index.html), an activity-bar Settings view (settings.js) with categories General, Hestia, Kybernetes, Phylax, Memory, Voice. Settings Panel opens with Ctrl+, per docs/MSS.md. Dashboard BFF proxies to Kybernetes /v1/admin with a service token.
- docs/MSS.md says approvals are single-use and bound to an action; Prosopon's approval endpoint accepts only allow_once or deny.

2.2 Gaps and risks I found by reading [RISK]. Each must be fixed or consciously accepted before Pyle exposes MSS beyond loopback.
R1. Default pairing role is admin. generate_pairing_pin(role="admin") and verify_pin_and_pair takes the role from the PIN record, so a phone paired by PIN becomes admin, with approval, dashboard-config and workbench rights. No least-privilege path from the CLI/UI today.
R2. No device identity. PairedDevice has no device id, no last-seen time, no user-agent/OS metadata, and revocation is by raw token. get_paired_devices() exists in code but no HTTP route lists devices (not seen in server.py). The UI cannot show or revoke one device by id.
R3. "Revoke" by an admin token wipes every device. There is no "revoke this one" for an admin viewing others.
R4. Loopback exemption vs tunnels. require_auth trusts request.client.host in {127.0.0.1, ::1} when not in LAN mode, and POST /api/auth/local-token hands out an admin token to loopback callers. An SSH -L forward, a tailscale serve mapping or any reverse proxy delivers remote traffic from loopback, with no forwarding headers in the SSH case, so neither source address nor header inspection can tell local from remote. With a loopback bind and remote mode off, an SSH-forwarded caller could obtain an admin token. (Admin routes are guarded separately, chat/session routes are not.) Not tested.
R5. /api/lochos/ws accepts the WebSocket without any auth check in the code I read (websocket.accept() first). It streams squad state. Not tested.
R6. Token lives in localStorage ("prosopon_token") and CSP allows script-src 'unsafe-inline'. Any XSS could read the token. T3 uses httpOnly cookies.
R7. PIN is global, 6 digits, with lockout that is global rather than per source address. Fine for a short LAN window; weak as the only gate for an internet-reachable route.
R8. Allowed hosts are a static list plus the machine's hostname/IPs. A Tailscale name, custom domain or new LAN IP is rejected until added by hand. Pyle routes must feed this list.
R9. Phylax states it is not an OS sandbox (phylax/THREAT_MODEL.md). A remote device that can drive the coding agent can cause shell commands inside the agent's sandboxed_bash. So "operate the agent" is effectively a powerful grant, same point T3 makes.
R10. TLS is self-signed only; phones will warn and the browser Secure Context needed for voice/mic is unavailable over plain HTTP.

3. DESIGN PRINCIPLES (PROPOSED)
======================================================================
P1. Local-first. No Pyle feature requires an MSS-operated or third-party relay. Core routes: LAN, SSH forward, owner-run reverse proxy. Tailscale (or another VPN the owner already runs) is optional and carries its own account and service dependency, which the spec does not hide. A self-hosted relay is deferred (section 13).
P2. Remote off by default. A fresh MSS binds loopback only. Turning remote on is an explicit owner action from a local, authenticated session or the terminal.
P3. Device identity first. Every remote client is a named, listed, revocable device with its own credential. No shared secrets.
P4. Least privilege by default. New devices get a Companion preset (chat + read), not admin. Powers are explicit scopes.
P5. Owner step-up for dangerous actions. Pairing new devices, widening scopes, enabling remote, and approving T2/T3-tier actions from a remote device can require confirmation on the host or an already-trusted owner device.
P6. Honest status. The UI shows what is actually reachable, which route is in use, and when nothing has been verified.
P7. Fail closed. If proxy awareness, TLS state or the auth store is uncertain, require a token.
P8. Prosopon owns the access boundary. Kybernetes stays on loopback and is reached only via Prosopon's service token (as DASHBOARD_SPEC.md already requires). Phylax stays the decision engine for agent actions; Pyle decides who may ask, Phylax decides what may happen.

======================================================================
4. THREAT MODEL (SHORT)
======================================================================
Assets: source code in the workspace, shell execution through the coding agent, model/GPU time, Phylax approvals, chat history, memory (LTHCM), settings, audit log.
Attackers considered: someone on the same Wi-Fi; a stolen/lost paired phone; a malicious web page in a paired browser (CSRF/XSS); a compromised other tailnet node; an internet scanner finding an exposed port.
Out of scope: attacker with host OS access, malicious local process under his UID (Phylax already says it cannot stop this).
Required outcomes: unauthenticated user can reach nothing except a login/pair page and a health endpoint; a lost phone can be cut off in one action and its live connections drop immediately; no device can silently gain more power than it was paired with.

5. FEATURE OVERVIEW (PROPOSED)
======================================================================
5.1 Access modes (host-side setting "Remote access")
 OFF            loopback only (default).
 LAN            bind a chosen private interface/IP only (not 0.0.0.0 unless the owner picks "all interfaces" with a warning).
 TAILNET (optional) HTTPS via tailscale serve mapping; needs a Tailscale account/service the owner runs; MSS stays bound to loopback behind it. Because requests then arrive from loopback, auth must not rely on source address (see 8.3).
 SSH            no listening change. UI/CLI shows the exact ssh -L command. Forwarded requests arrive from loopback with no proxy headers, so they are authenticated like any other request (see 8.3).
 CUSTOM URL     owner-run reverse proxy with a stated public hostname; requires TLS and a trusted-proxy setting.
Modes can be combined. Each enabled mode is a Route (section 7).

5.2 Pairing methods
 - One-time pairing link + QR (primary). 5 minute TTL by default, single use, carries a label and scope preset chosen by the owner when creating it.
 - Short code fallback (6+ digits) shown only on the host console/Manage Devices window, for people who cannot scan. Longer entropy than today (8 digits or word code) and per-source rate limit.
 - Optional host confirm: when a device redeems a link, the host shows "Pixel 8 on 192.168.1.40 wants to join as Companion. Allow / Deny." Default on. [OPEN: default on or off]
 - CLI pairing for headless host: prosopon device pair.

5.3 Sessions
 - Browser: httpOnly, SameSite=Lax (Strict if no cross-site need), Secure when TLS, cookie with random session id.
 - Non-browser clients: bearer token. DPoP binding is optional later (T3 has it); not needed v1.
 - Server stores only hashes. Per-device TTL (default 30 days, fixed expiry; sliding is an optional setting), owner can set per device: 1 day / 7 / 30 / 90 / never expire (never = warning).
 - Short-lived websocket tickets (60 s, single use) for all WebSocket endpoints.

5.4 Manage Devices window (see section 9)
 List of devices with live connection state, scopes, last seen, route used; revoke; edit; create pairing link; audit trail.

5.5 Settings > Remote Access section (see section 10).

7. ROUTES (PROPOSED, MIRRORS T3 CONCEPT BUT ADJUSTED FOR BROWSERS)
======================================================================
- A Route is one way to reach this MSS host: LAN address, tailnet name, SSH forward, custom URL.
- Device scopes are per DEVICE, not per route, and apply on every route. (T3 shows a per-route Permissions panel because its T3 Connect and direct sessions can differ. MSS has one device credential store, so the Routes tab only shows route state; scopes are shown on the device.) Every route uses the same authorization code path.
- Browser origins differ per route (https://host.lan:8000 with a LAN cert, https://host.tailnet.ts.net, and for SSH, https://localhost:PORT through the tunnel). Cookies and localStorage do not follow a hostname change, and an HTTPS page cannot call an HTTP LAN endpoint (mixed content). Consequences:
  * Browser clients are enrolled PER ROUTE ORIGIN. A phone paired over Tailnet has no session on the LAN origin until it enrols there too. It is the same device_id on the host; each origin gets its own session/cookie. The pairing flow offers "also enrol this route" (fresh link, or on-device confirm from an already-trusted session).
  * A browser tab or PWA is still sandboxed to one origin: it cannot pin certificates, and it cannot hold a credential usable across other origins. Automatic failover across routes, certificate pinning and a cross-origin credential store are therefore claimed ONLY for a native client (Phase 4, separate decision). For browsers and PWAs, v1 does manual route choice with "open this route" links and no automatic failover. A browser-compatible failover design would need its own justification and is not assumed.
  * Authenticated remote access is TLS-only. Plain HTTP may serve at most a non-sensitive landing/setup page (host name, how to reach the TLS route, certificate fingerprint to compare). Plain HTTP never accepts credential redemption, cookies or bearer tokens. An HTTPS page is never asked to call an HTTP route.
  * SSH-forwarded browser route: HTTPS through the SSH tunnel only. Prosopon serves HTTPS on the host and the user forwards to it (https://localhost:PORT), checking the host cert fingerprint shown on the host. There is no plain-HTTP exception. The session audience is that exact origin and the same rules as every other route apply.
  * Credentials are never placed in URLs beyond the one-time pairing credential, which is removed from the address bar after redemption (redirect, Referrer-Policy: no-referrer).
- Host identity verification: before a device sends a pairing credential it should confirm it reached the right host. Trusted cert: the cert. Self-signed LAN: a native client checks the fingerprint carried in the link/QR; in a browser the owner compares the fingerprint shown on the host with the one the browser displays in its certificate warning (manual check, not enforced by MSS). No credential redemption over plain HTTP, ever.
- Linking a second origin to an existing device: the client never supplies device_id or label as proof. Enrolling route B for an existing device requires a device-link proof: an owner/Owner-device-approved, single-use link request that the host binds server-side to that device_id (or an already authenticated session on route A requesting a link-token that is redeemed on B). Without proof, enrolling on B creates a NEW device record.
- Session audience binding: each session is stored server-side with its route/origin (audience). The server rejects a session credential presented on a different route/origin than it was issued for, regardless of cookie scoping; host-only cookies are a browser convenience, not the control.
- Origin, CORS and CSRF per route: allowed_hosts and allowed_origins are generated from enabled routes only, CORS is not opened to other origins, cookies are host-only (no Domain attribute), mutating requests need SameSite cookie plus Origin check plus a custom header, and trusted proxies are explicit (8.3).
- Route status honesty: the host can verify that a listener exists and that its own TLS/cert is valid. It cannot prove a phone can reach it. The UI shows "Listening (host checked)" and shows "Reached by a device at <time>" only after a real device connection over that route. Never "Active" from a host-side probe alone. A "Test from this device" button checks reachability from the device in use.
- Host publishes its current addresses over an authenticated endpoint so enrolled devices can learn new LAN/Tailnet addresses; learned routes are suggestions the owner can review.
- Tailnet detection: do not label an address in 100.64.0.0/10 as Tailscale unless `tailscale status` confirms it (T3 caveat).

8. SECURITY REQUIREMENTS (PROPOSED)
======================================================================
8.1 Scopes
 chat:read            read sessions and history
 chat:operate         send messages, voice, create/delete sessions
 workbench:read       file tree, file view, diffs
 workbench:write      edits made by the user through the UI (not agent)
 agent:operate        start/stop MSS coding-agent runs, dispatch Lochos tasks
 approvals:resolve    allow_once/deny for Phylax approval prompts
 approvals:resolve_high  same for T2/T3-tier actions (shell mutation, network, install)
 squad:read / squad:operate   Lochos view / dispatch+resolve attention
 pinax:read           tool catalogue
 settings:read / settings:write   dashboard config view / apply + rollback
 models:operate       load/unload Hestia models
 diagnostics:read     traces, audit-log, GPU telemetry
 access:read / access:write   list all devices / manage devices and pairing
 Self endpoints (see 11) need only a valid credential and no scope: read own device record and scopes, rename own device, sign out. They never expose other devices.
 remote:configure     change access mode and routes
Notes: agent:operate is functionally close to shell access because the agent has sandboxed_bash and Phylax is not an OS sandbox. The UI must say so when granting it.

8.2 Presets
 Viewer       chat:read, workbench:read, squad:read, diagnostics:read
 Companion    Viewer + chat:operate. (phone default; cannot approve, cannot start agent runs)
 Operator     Companion + agent:operate, squad:operate, approvals:resolve (not _high), models:operate
 Owner        everything incl. settings:write, access:write, remote:configure, approvals:resolve_high
 Custom       any list
 Rules: only an Owner device (or the host via the host-owner credential) can create an Owner link. A device can never create a link with scopes it does not hold. Default: one Owner device (the host's own "This computer" device); more Owner devices are an optional owner choice.

8.3 Auth enforcement
 - Single authorization dependency used by every route and WebSocket: authenticate -> resolve device -> check scope. Replaces the current mix of require_auth / require_admin_auth.
 - NO loopback exemption at all. Every application endpoint and WebSocket requires a device credential, whether or not remote mode is on and whatever the source address or headers. Only /api/health (minimal), /api/auth/descriptor and /api/auth/redeem are unauthenticated. This replaces the idea of inferring "local" from bind address or headers, which cannot work for SSH forwards (R4).
 - Local bootstrap without a loopback exemption: (a) at startup Prosopon writes a host-owner credential file in data_dir (mode 0600, owned by the running user, rotated on each start and on demand). (b) `prosopon open` reads that file, mints a one-time, 60 second, single-use local login link and opens the browser (or prints it); the browser redeems it for a normal cookie session on a device named "This computer (host)". (c) The same file lets the CLI call the API. Proof of local access is therefore filesystem access under the owner's UID, which an SSH-forwarded caller does not have. (d) POST /api/auth/local-token is removed. Anyone who can read the host-owner file already has host-level access, which section 4 excludes.
 - Trusted-proxy handling: forwarding headers (X-Forwarded-*, Forwarded, Tailscale-User-*) are ignored unless the direct peer is in remote.trusted_proxies. They are used only for logging the client address and scheme, never for granting access.
 - Add scope checks to every currently admin-only route, mapping /api/dashboard/* to settings:*/models:*/diagnostics:*, /api/approvals/*/resolve to approvals:*, /api/workbench/* to workbench:*, /api/lochos/* to squad:*, /api/pinax/* to pinax:*.
 - WebSocket /api/lochos/ws and any new streaming endpoint must authenticate before accept using a one-time ticket (fixes R5).
 - Cookie session for browsers; bearer for scripts/CLI. Remove token from localStorage; if kept for non-browser clients, show it once.
 - CSP: remove script-src 'unsafe-inline' (move inline JS to files, use nonces). Required before any non-LAN exposure (R6).
 - CSRF: SameSite cookie + Origin check (already present) + custom header on mutating requests.
 - Rate limits: per source IP and per link; exponential backoff; global lockout only as last resort. Pairing credential at least 128 bits for links; codes at least 8 digits plus per-IP limit (R7).
 - TLS: required for any non-loopback, non-tailnet route; tailnet HTTPS via tailscale serve counts as TLS. Self-signed is allowed on LAN with a fingerprint shown in Manage Devices so the phone can verify it (R10). Option for the owner to supply their own cert.
 - High-risk remote actions step-up: approving T3-tier actions, enabling remote access, widening scopes and revoking the last Owner device require confirmation via the host-owner credential (host console or `prosopon open` session) or from an Owner device on a TLS route after fresh re-authentication. Source address is never the proof. Strictness is an optional owner choice.
 - Remote approvals show the full action card (verb, canonical resource, arguments digest) already in Phylax's approval contract, so a phone approves a specific action, not a generic "yes".

8.4 Revocation
 - Revoke one device: invalidate sessions, close its open WebSockets/SSE within 1 second, pending pairing links it created are revoked, audit row written.
 - Revoke all others (keep this one).
 - Panic lockdown: one action (button + CLI prosopon device lockdown) disables remote access, revokes all non-host devices, invalidates all pairing links. Requires the host-owner credential or an Owner device with fresh re-authentication.
 - Expired devices are marked revoked_reason=expired and listed in History for 30 days.
 - Revoke must be race-safe with live requests (check revoked_at on each request, not only at login).
 - What revocation can and cannot undo. Revocation stops FUTURE requests and closes streams. It cannot roll back side effects that already committed. Defined behaviour: (a) a request not yet dispatched to Kybernetes/Phylax/Hestia is cancelled; (b) an agent run the device started is, by default, stopped at the next safe point (cancel-before-dispatch applies to the next tool call), with a "keep running" option chosen at revoke time; (c) a tool call or file write already executed stays executed (the git milestone checkpoint can roll back files, but only as a separate owner action, never automatic); (d) a Phylax approval already consumed stays consumed, and a pending approval shown to that device can no longer be resolved by it; (e) the revoke dialog lists the device's running agent runs and recent actions so the owner can see what to review. Audit rows record what was cancelled and what had already executed.

8.5 Auditing
 Every access change and every remote approval is written to access_audit. Manage Devices has an Activity tab. Audit entries about approvals link to the Phylax audit record id.

9. MANAGE DEVICES WINDOW (PROPOSED UI)
======================================================================
Location: Prosopon web workbench. Opened from (a) Settings > Remote Access > "Manage devices", (b) the existing lock/pairing icon in the header (replaces the PIN-only modal), (c) command palette "MSS: Manage Devices", (d) Ctrl+Shift+D. 12. HOW IT FITS THE REST OF MSS
======================================================================
- Prosopon: owns everything above. Reuse PairingManager's hashing and file-lock ideas, but replace its storage and role model.
- Kybernetes: keep bound to 127.0.0.1:8081; Prosopon passes the authenticated device id and scopes in a signed header or request field so Kybernetes admin routes and traces record who did what. Kybernetes should refuse unsigned requests when remote mode is on. [OPEN: signing method]
- Phylax: remote approvals use the same approval contract. Add fields to the audit record: approver_device_id, route, remote (bool). Add an optional Phylax policy rule: "T3 tier actions cannot be approved from a remote device".
- Lochos (squad/OpenRig-style work): squad view and attention resolution are scoped (squad:read/operate). A phone that sees "attention needed" and resolves it is the natural headline use case. Keep this separate from the OpenRig/Lochos integration proposal; just consume its endpoints.
- Hestia: model load/unload from a phone is models:operate only.
- Voice: browsers need a Secure Context for the microphone. Tailnet HTTPS or a trusted cert solves this; plain HTTP will not allow mic on phones, and per section 7 it is not used for authenticated access. Show that in the Routes tab.
- Notifications: no cloud push. Phase 4 option: optional ntfy/Matrix/local webhook the owner runs, off by default. T3's push relay is not copied.

13. PHASES (PROPOSED ORDER)
======================================================================
Phase 0 - Minimal pre-exposure gate (no remote route is supported before this passes)
 - Remove the loopback exemption and /api/auth/local-token; add host-owner credential + `prosopon open` local bootstrap (8.3).
 - Authenticate every endpoint and WebSocket before accept (fixes R4, R5).
 - New pairings default to least privilege, not admin (fixes R1); device ids exist.
 - Remote off by default.
 Gate tests: T1, T2, T3, T13 (section 14). Nothing else may be claimed passing yet.
Phase 1 - Transport hardening and device registry (LAN only; this is the gate before any tunnel route)
 - httpOnly cookie sessions, WebSocket tickets, CSP without unsafe-inline, per-IP/per-link rate limits, stronger pairing credentials, TLS handling and fingerprint display, trusted-proxy handling, CSRF checks (R6, R7, R10).
 - SQLite device registry, presets/scopes, pairing links + QR, Manage Devices window (Devices, Pending, Activity), revoke one/others, CLI device commands, host-confirm, audit chain.
 Gate tests: T4-T12, F1, F2a, F3, F6, F7, U1-U3. Until the Phase 3 gate, remote devices are denied agent operation and all approvals of T2/T3-tier actions (and all remote approvals unless explicitly enabled), so Phase 1 ships view/chat-style presets only.
Phase 2 - Routes (only after the Phase 1 gate passes)
 Routes tab, per-route enrolment, allowed-host auto-management, SSH instructions, reverse proxy, optional tailscale serve integration, route status honesty, learned routes. Gate tests: F4', F5, T14, T15.
Phase 3 - Remote approvals and operations
 Step-up, remote approval policy and approval behaviour, agent-run handling on revoke (stop at next tool call / keep running), lockdown, doctor checks, own-cert TLS. Gate tests: T12 (extended), F2 (full), T16.
Phase 4 - Optional extras (each needs its own decision)
 Self-hosted relay; native client with credential store and automatic route failover; DPoP-bound tokens; local push; multi-host load balancing; per-device IP pinning.

14. TESTS AND PASS/FAIL CRITERIA
======================================================================
Security
 T1 Remote off: connect from another host to the LAN IP -> connection refused/no listener. PASS if nothing answers. (Phase 0)
 T2 Unauthenticated request to every route (iterate the route table) from loopback, from a non-loopback address, through an SSH -L forward, and with/without X-Forwarded-For: 127.0.0.1 -> 401/403 except health, descriptor, redeem. PASS if zero exceptions. (Phase 0)
 T3 Unauthenticated WebSocket connect to every WS route -> closed before accept. PASS. (Phase 0)
 T13 Local bootstrap: `prosopon open` works for the owner; the host-owner file is mode 0600; a process without file access cannot obtain a session, including via SSH forward; /api/auth/local-token no longer exists. PASS. (Phase 0)
 T14 Per-route enrolment and audience binding: copy a valid session cookie/bearer from route A and present it on route B (set manually, bypassing browser cookie scoping) -> server rejects it (audience mismatch). Enrolling B without a device-link proof creates a new device; with proof it joins the same device_id; a client-supplied device_id or label is ignored; revoking the device kills sessions on both. PASS. (Phase 2)
 T15 Forwarding headers from a peer not in trusted_proxies are ignored for auth decisions; the mixed-content case (HTTPS page to HTTP route) is blocked and shown as such. PASS. (Phase 2)
 T16 Agent-run handling on revoke (extra to T8): revoke while an agent run started by that device is mid-way -> stops at next tool call, or keeps running if chosen; revoke dialog lists the runs; audit records it. PASS. (Phase 3)
 T4 Pairing link: single use, expires at TTL, revoked link fails, wrong credential fails without revealing why. PASS.
 T5 Brute force: 50 bad codes from one IP -> blocked; another IP still unblocked until its own limit. PASS.
 T6 Scope matrix, phase-aware: for each preset, call every route and compare with the expected allow/deny table. Phase 1 table: Viewer and Companion are grantable; Operator and remote Owner are rejected at creation; the host's own Owner device works; agent-run and approval routes deny remote devices. Final Phase 3 table: the full matrix of section 8.1 including Operator and Owner. PASS if the table for that phase is identical. (Phase 1 and re-run in Phase 3)
 T7 A device cannot create a link or edit scopes beyond its own scopes. PASS.
 T8 Revocation: revoke a device with an open SSE and WS and an in-flight request -> sockets close within 1 s, next request 401, undispatched work cancelled before dispatch (mandatory from Phase 1), already-executed writes/tool calls unchanged and recorded in audit. PASS. (Phase 1)
 T9 Legacy tokens imported as scoped devices (or invalidated per decision) and visible in the list. PASS.
 T10 Token/credential never appears in logs, audit, device list, or error bodies (grep test). PASS.
 T11 CSRF: cross-origin POST with cookie rejected. PASS.
 T12 Lockdown disables remote and revokes all non-host devices. PASS.
Functional
 F1 Pair a phone over LAN via QR, send a chat message, see it in history on the host. PASS.
 F2a (Phase 1) Companion/Viewer devices cannot see or call Approve or agent-run endpoints; Operator/Owner presets are not grantable to remote devices until the Phase 3 gate (server rejects with a clear message). PASS.
 F2 (Phase 3, full) Operator can approve T1/T2 but not T3 when policy says require_host_confirm; Phylax audit records approver device and route. PASS.
 F3 Manage Devices shows connected dot flip within 3 s of connecting/disconnecting. PASS.
 F4' Route reachability honesty: a route shows "Reached by a device" only after a real device connection; a host-only probe shows "Listening, host checked". Automatic failover is tested only if a native client is built (Phase 4). PASS.
 F5 Host IP changes (new Wi-Fi) -> learned route updates; allowed_hosts follows; no manual edit. PASS.
 F6 Two devices same label are distinguishable (id suffix, OS, last IP). PASS.
 F7 Audit hash chain verifies; tampering with one row is detected. PASS.
UI/visual
 U1 Manage Devices at 360, 768, 1440 px: no clipped text, actions reachable by keyboard. Check with screenshots.
 U2 Unverified route never shows a green state. PASS.
 U3 Empty states and error states render real messages, no placeholder data.
Claims that are NOT proven by these tests: hardware, GPU or real-model behaviour, third-party VPN behaviour, browser quirks on every phone. Those need manual verification on the owner's own devices, and no one has run them.

15. ACCEPTANCE CRITERIA (FEATURE COMPLETE)
======================================================================
1. A fresh install exposes nothing beyond loopback, and even loopback and SSH-forwarded callers must authenticate.
2. The owner can pair a phone in under 60 seconds with a QR, with least-privilege defaults.

4. Every route and WebSocket enforces scopes through one code path.

6. The doctor command reports each risk in 2.2 as fixed, accepted or open.
7. All of section 14 passes.
