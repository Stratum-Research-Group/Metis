HESTIA - model serving layer. New project scaffold and first build. Follow these instructions exactly. Ask before deviating.

CONTEXT
Hestia is the model serving utility for a local AI stack. Today every project (LTHCM, Dianoia) would load its own copy of a model. Hestia makes models a shared utility: one service hosts them, everything else calls an API.

HARD CONSTRAINTS
- Everything local: no paid APIs, no hosted models.
- Backend is llama.cpp server (must work on both RTX 5060 Ti 16GB / Blackwell and Tesla V100 SXM2 16GB / Volta via PCIe adapter). Design the backend behind an interface so vLLM can be added later.
- VRAM-aware: assume a 16GB per-card budget; never load a model that does not fit.

BUILD, IN THIS ORDER

1. REPO SCAFFOLD
- New repo "hestia", Python package, pyproject.toml.
- Model registry as a YAML file: per model - name, GGUF path, quantization, context size, default sampling params, GPU target.

2. SERVER MANAGER
- Launches and manages llama.cpp server processes for registered models.
- Health checks, logs capture, automatic unload after an idle timeout (default 10 min) to free VRAM.

3. API
- OpenAI-compatible /v1/chat/completions endpoint proxying to the running backend.
- /models endpoint listing the registry with loaded/unloaded status.

4. CLI
- hestia list / hestia load <name> / hestia unload <name> / hestia status showing VRAM use per model.

OUT OF SCOPE
- vLLM backend, multi-GPU sharding, auth, remote access, fine-tuning.

DEMO
- Register one 8B GGUF instruct model, hestia load it, answer one curl chat request, hestia status shows it loaded, auto-unload fires after idle timeout.
