# Krisis spec v4: remaining issues before a build freeze

Reviewed 2026-09-30. Source: [krisis-spec-v4.txt](krisis-spec-v4.txt), compared with the [v4 review-request assessment](krisis-v4-review.md), prior v3 spec, and the local stack documents. The `/home/akarta/Projects/krisis/` copy matches. This is a specification review; Krisis has not been implemented or benchmarked in the reviewed directory.

## Verdict

V4 is materially stronger: it separates Foundation from quality promotion, makes grounded support a hard gate, audits verifier error and claim extraction, defines candidate generation and routing ownership, compares selectors on the same candidate set, and separates policy replay from feature recomputation. It is close to a buildable contract.

**Do not freeze it yet.** The prose calls a worked example and fixtures “canonical companion artifacts,” but no JSON manifest or fixture files are present. Several fixtures still have more than one possible outcome, and the sample profile requires an optional logprob feature with no grounded fallback. These are small, concrete gaps rather than a need for another architecture rewrite.

## Suggested v4.1 minimum patch

1. Add `krisis-policy.schema.json`, a canonical `krisis-policy-0.1.json`, and pure-policy fixture JSON files. Include full profile-selection and aggregate-reason tables, numeric feature ranges and exact score/tie/equality rules. Treat the prose example as explanatory only once the JSON is frozen.
2. Add a support-only grounded profile. Specify what happens when support verifier, calibrated confidence or Hestia logprobs are unavailable for **each** question class and `requires_grounding` setting.
3. Freeze the verifier release envelope in a separate versioned audit card: claim extraction, support false positives, coverage, critical slices, sample sizes, confidence method, version invalidation, and deactivation/reactivation drill. A supported span is evidence grounding, not proof that the source is true.
4. Make fixtures B, D, F, G, I, J and L exact and single-valued. For the injection fixture, keep a stubbed policy case and a separate real-model attack test.
5. Run a Hestia baseline and a full Kybernetes API benchmark on the target 16 GB hardware. Freeze absolute turn, generation, verifier and selector budgets from those results; add UI timing when Prosopon exists.

## Answers to v4's open questions

- **Weights/dev split:** the 0.7/0.3/0.55 values are examples only. Tune on a new versioned Dokime Krisis development suite, grouped by source/document family and query cluster, with model/verifier/calibration versions fixed. Seal the final test before weight search; the stack owner approves the manifest and Dokime recomputes its evidence.
- **Verifier on 16 GB:** prefer a separately versioned local verifier that can be run within measured Hestia admission limits, ideally a different model family from the generator. If only a shared family fits, report the correlated-error risk and require stronger human-audited false-support slices; do not claim independence merely because there are two calls.
- **Extraction and audit bounds:** derive target limits and sample sizes from the intended risk/coverage policy and a pilot, then preregister them before final testing. Use upper confidence bounds for false support and missed claims, including multi-claim, negation, quantity and scope slices. If a bound cannot be met, grounded promotion remains off.
- **Adjudication queue:** set a finite queue cap, maximum age and sampling policy in the manifest after measuring throughput. Overflow must produce a typed verifier-unavailable/abstain state for affected grounded requests; it must not silently mark claims supported.
- **Retention:** define concrete durations by sensitivity class before a user-facing Foundation release, including raw query/answer text, derived features, audit metadata and human labels. Deletion must invalidate any replay that depends on removed content and record what remains auditable.

The v4 design is close. Its remaining work is to replace open choices with canonical artifacts, exact fallback and outcome tables, and a measured verifier envelope. Until then it is a strong draft, not a fully frozen production build contract.
