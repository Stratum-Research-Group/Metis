METIS TAKEAWAYS (rev 2) from CompoWorld / AgentEnv (arXiv 2609.33665v2 + AgentEnv repo @1deac75)
Date: 2026-10-20. Metis facts verified against a fresh clone at 7eb7cd27454c16728f222354ad94af430c41ddc2 (current HEAD). These are proposals and pattern notes, not implementation instructions. No new experiment proposed.

1. PAIDEIA - completion-focused reward weighting (proposal, not drop-in). Metis already has a GRPO walk-policy engine (paideia/paideia/training/grpo.py, 197 lines, per spec metis-grpo-walk-policy-spec-e6633b6a.txt): step-level scalar rewards with H1-H8 anti-hacking penalties, and group-normalized advantages A_i = (R_i - mean)/(std + eps) [verified in source]. CompoWorld's contribution is one layer up: when an episode is judged by MULTIPLE rubric criteria, weight criterion j by w_j = lambda + (1 - group pass rate p_j) so unmet criteria dominate the advantage (paper Eq 5, p.6; gradient analysis App A, p.15). Adopting it here means (a) defining multi-criterion rubrics for walk episodes - the current reward is a single scalar plus penalties, so criteria must first exist; (b) computing per-criterion group pass rates per rollout group; (c) recombining into one reward before the existing group normalization. That is a design change to the reward engine, not a one-line edit. Evidence caveat: in the paper's own reporting, RL added only +1.2 points average over SFT and the reweighting comparison is a single run pair (Sec 5.3.3, App A) - treat as an unproven refinement worth a small test if walk-episode rubrics ever exist, not a priority.

2. KYBERNETES / PINAX - lazy tool discovery is already the Metis design; CompoWorld is external corroboration, not a missing fix. Pinax is implemented at HEAD: catalogue + SQLite db + scanner + prober with "multi-level retrieval without prompt drowning" (levels 0-2) (kybernetes/kybernetes/pinax/, catalogue.py docstring) and a seed inventory of 68 curated entries (pinax/seed.py) [verified in source]. CompoWorld's runtime uses the same idea as four meta-tools: list_services / list_tools / describe_tool / call_tool (verified in the released trajectory records). Takeaway: the pattern trains well in their setting, which supports keeping describe-on-demand as Pinax's contract. Do not cite their 10,130-tool figure as scale proof for the runtime: each training session mounts K=5 services plus 5 distractors (paper Sec 5.1), and only 20 curated trajectories are public.

3. DOKIME - stateful task packaging (new capability, proposal). Dokime's current tasks are Python classes behind a Task protocol with entry-point discovery, QA-style (ARC, GPQA, AIME, Zebra, epistemic, pinax_lookup_50) [verified in source: dokime/src/dokime/tasks/]. CompoWorld/Skill2Env show a different contract worth adding when Metis needs whole-stack workflow evals: task = (instruction, initial state, goal, verifier) where the verifier checks final-state rubric conditions, not the action sequence; weighted rubric items aggregate to 0..1 with deterministic checks first and an llm_judge only where state can't be checked mechanically (76 deterministic vs 22 judge items across their 20 example tasks). Their Harbor-style file layout (instruction.md, task.toml resource limits, environment/{Dockerfile,setup.sh,workspace/}, tests/{verify.py,eval_spec.json}) is one concrete packaging option; the verifier-contract idea matters more than the layout. Static inspection only - their fixture code was not executed.

4. KYBERNETES/PHYLAX test fixtures - typed-state mock services + independent test authorship. Their service recipe: typed Pydantic state per service, tools as state transitions returning a uniform {"success", "data"/"error"} JSON, self-tests repaired to green, then a SEPARATE agent session writes adversarial spec-derived tests and failing tools are quarantined (paper Sec 4.1). The transferable rule is the independent second-pass test writer - fixtures not graded only by their own author's tests. This maps onto how MSS/kybernetes mock tools for tests could be built. Static pattern note; their implementation is not released.

5. STOMA/DIANOIA data shape (minor). If trajectory-style training data is ever needed (e.g. the Anadrome walk-replay spec), their released JSONL schema (tools / messages incl. reasoning_content / meta{services, capabilities, rubric_score, n_tool_calls} / source) is a working reference format [verified repo].

6. LTHCM - no supported change. This work is environment synthesis for agent training, not memory or retrieval. Nothing tested here bears on LTHCM's indexing or retrieval. At most indirect: mock services could one day seed eval fixtures for the whole-stack Dokime eval. Do not route this into the LTHCM paper.

7. Hardware - no feasibility claim made. I did not run a training-memory or offload analysis. As described, the paper's recipe (3-epoch SFT then GRPO on a 35B-A3B) is a datacenter-scale run; whether any scaled-down variant fits the 5060 Ti / V100 is unverified and would need its own analysis. Items 2-4 are design patterns that do not require training anything.

8. Unaffected lines: no bearing on JitMem, the JAZ review outcome, or the shelved SwiLA path.
