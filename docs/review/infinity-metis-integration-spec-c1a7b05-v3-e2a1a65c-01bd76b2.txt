1. TWO TRACKS, AND AN HONEST DEPLOYMENT GATE
--------------------------------------------
TRACK A - BRIDGE (extension-only): new code alongside Infinity that makes it
  speak to Metis. No Infinity source changes. This is what Nick asked for.
TRACK B - HARDENING (modifies or compensates Infinity): fixes for the defects
  the c1a7b05 review found, required before any deployment beyond a watched
  single-user demo on one machine.

The bridge is useful without Track B for local experimentation. It is NOT
deployment-ready without it: loopback binding and SSH tunnels reduce network
exposure, but they do not fix a browser on the same machine driving the
unauthenticated daemon WebSocket, a local malicious process calling sandbox
tool endpoints, or work silently lost/duplicated or retried without bound in
the persistence/replay paths. Track B items are in section 4; each is either a
minimal patch to Infinity (local branch, reported, test-covered) or a
demonstrably complete compensation. "Deployment" anywhere in these specs means
Track B landed and its gates passed.

Delivery semantics, stated once and used everywhere below: durable outbox +
idempotency gives AT-LEAST-ONCE delivery plus dedup on paths we control. It
does not make arbitrary external effects exactly-once. External effects need a
target that is idempotent, or explicit reconciliation of UNKNOWN outcomes
(crash between "effect sent" and "result recorded" = unknown, surfaced for
reconciliation, never silently retried or silently dropped).

3. TRACK A - THE BRIDGE (what "speak to Metis" concretely means)
----------------------------------------------------------------
Two separate things must not be conflated:
  MODEL PATH - where an Infinity agent's own LLM completions come from.
  TOOL PATH  - Metis capabilities an Infinity agent can invoke as tools.

A1. infinity-provider-hestia (new crate; model path, Phase 1)
    - list_models: GET {HESTIA_URL}/v1/models with Bearer token; map each entry,
      context_window <- context_size [VERIFIED present]; if a model lacks
      context_size, fail loudly for that model - never invent a number.
    - invoke_model: POST /v1/chat/completions, stream=true; CompletionRequest ->
      OpenAI chat format; SSE chunks -> StreamChunk (chunk-shape guidance:
      infinity-provider-rig/src/convert.rs:319).
    - Unsupported content/capability handling: request shapes Hestia cannot
      honor (image content when supports_image_input=false, tool-call shapes
      the mapping does not support, unsupported parameters) FAIL EXPLICITLY
      with a clear error. No silent placeholder, no silent discard, no silent
      downgrade. Capabilities are advertised in ModelEntry exactly as supported.
    - Error classes: 401 fatal; QueueTimeout/503 retryable-with-backoff;
      connect-refused fatal with "Metis not running" clarity.
    - Config from env at process start: HESTIA_URL, HESTIA_SERVICE_TOKEN.
      Never logged, never in providers.json.
    - Runs on the rig only in Phase 1. Pi/satellite model access routes through
      the gateway (fleet spec P3) with per-node credentials; the shared service
      token never leaves the rig.
    - Default-model question (providers.json ordering) is Nick's decision D1;
      list Hestia first only if D1 is answered "direct".

A2. metis.ask tool (tool path, Phase 1) - the full-turn tool
    - One RAP toolset server (rig-side) exposing exactly one tool initially:
      metis.ask. It calls Kybernetes POST /v1/chat/turn [VERIFIED route], so a
      call goes through the 7-stage pipeline (Dianoia, Krisis, Phylax gating).
      That is deliberately the full pipeline as a TOOL; it is separate from the
      model-path decision in D1, which concerns where the calling agent's own
      completions are generated.
    - Streaming semantics: subscribe to the turn's SSE stream; map TurnEvents:
        content_delta    -> tool progress/result content
        approval_request -> RAP user-choice callback (RapUserChoice,
                            response_url); NEVER auto-resolve an approval.
                            The human answer goes back through
                            /v1/approvals/{id}/resolve [VERIFIED route].
        trace_complete   -> final result incl. citations
        error            -> tool error, classified
      STOP GATE: before implementation, verify the exact TurnEvent schema and
      stream route against the pinned Kybernetes source. If the schema or
      semantics differ from the above, stop and report - do not guess.
    - Async contract: return at once, deliver events and the final result via
      the invocation's callback channel (A4), so the calling agent hibernates
      during slow turns. Bound every wait with a timeout and a cancellation
      path (depends on Track B H5 for runtime support; bridge records the
      dependency).
    - Auth/scopes: the toolset holds the Kybernetes token server-side and
      requires its own bearer token from callers. A turn can reach Phylax-gated
      actions; approval requests pass through unchanged (above).

A3. Phase 2 tools - boundary contracts only, NOT built in Phase 1
    metis.memory_search and metis.ingest stay unbuilt until each STOP GATE
    clears:
      - memory_search: read-only retrieval. Contract in: query string, k, epoch
        bounds. Out: ranked passages with provenance ids. Auth: a memory-read
        scope distinct from chat. STOP GATE: the exact Kybernetes/LTHCM route
        and its authorization semantics are unconfirmed in pinned source;
        confirm route + scope model first, else report blocked.
      - metis.ingest: submit a Stoma ingestion job. Contract in: document
        reference + metadata; out: job id; completion delivered via callback.
        Auth: ingestion is a WRITE into memory - its own scope and a Phylax
        policy; never bundled with read tools. STOP GATE: confirm the Stoma
        submission route and its auth in pinned source first.
    SSRF protection for all tools: the toolset calls only configured,
    allowlisted destinations (HESTIA_URL/KYBERNETES_URL from server-side
    config). It never follows URLs taken from invocation arguments.

A4. Callback channel security (one invocation = many events)
    One invocation emits a STREAM of callbacks: progress events, zero or more
    approval requests, retries of any of these, and one final result. So the
    credential is NOT single-use-per-callback:
      - The daemon side issues one invocation-scoped, EXPIRING callback
        credential embedded in the callback_url.
      - Every callback event carries a unique event id and a monotonic
        sequence number within the invocation (binding).
      - The receiver authenticates the credential on every event, dedups by
        event id (idempotent acceptance of retries), and detects gaps by
        sequence.
      - Lifecycle: the final result event finalizes the invocation. The
        receiver then keeps a bounded, authenticated dedup receipt (tombstone)
        for a documented replay horizon: retries of already-accepted event ids
        are acknowledged WITHOUT reapplying effects (covers ACKs lost after
        acceptance), new events for the finalized invocation are rejected, and
        the receipt expires at the horizon's end.
      - Destination trust: the invocation-supplied callback_url alone is NOT
        trusted. The callback destination is registered/enrolled for the
        caller at session or invocation setup; the toolset sends only to that
        registered endpoint, follows no redirects, pins the DNS resolution
        made at registration, and rejects the send if a later resolution
        differs (DNS-rebinding defense).
      - Events carry only the event ids/sequences the toolset can prove for
        the invocation it is serving.
    DEPENDENCY, stated plainly: the daemon's callback receiver has no
    authentication at this HEAD [VERIFIED], so the receiver side of this
    contract requires a Track B patch or an authenticating proxy in front of
    the receiver. It CANNOT be implemented solely inside the external toolset.

4. TRACK B - HARDENING (required before deployment; each = patch or verified
   compensation, minimal and test-covered, reported per item)
---------------------------------------------------------------------------
  H1. Daemon WebSocket: add authentication and Origin checking [gap confirmed
      at this HEAD]. Loopback does not fix a hostile page in the user's own
      browser reaching 127.0.0.1.
  H2. Sandbox-local: stop binding 0.0.0.0 unauthenticated
      [crates/sandbox-local/src/server.rs:25 confirmed]; loopback bind plus an
      authenticated local channel.
  H3. GitHub webhook: fail closed when the signature header is missing,
      whenever a secret is configured (review reproduced acceptance at this HEAD).
  H4. Durable effects: every path causing an effect or ingestion (tool
      results, callbacks, subscription events, migrations) gets a durable
      inbox/outbox with idempotency keys - AT-LEAST-ONCE delivery plus dedup on
      controlled paths [review: swallowed/non-atomic writes, fail-open dedup and
      child replay]. For effects on systems we do not control: require target
      idempotency, or record UNKNOWN outcomes for explicit reconciliation.
      No exactly-once promise is made or implied.
  H5. Bounded retries: fix the retry budget reset on partial streams; add
      cancellation for every long wait [review finding].
  H6. MCP bridge: complete notification/response parsing and lifecycle handling
      [review finding].
  Until H1-H6 (or demonstrated complete compensations) land, all deployment
  language in this spec and its companions means "watched single-user demo".

    section 3): Pis may run Infinity satellites and/or Pi-local RAP toolsets;
    the rig runs Metis. Roles are chosen per node, not asserted here.

    assumption, not a ban - R4 in the fleet spec is the gated future option).
  - Runtime compatibility is a VALIDATION STEP, not a mandate: enrollment
    probes each Pi's model/RAM/OS/arch; the build target is chosen from probe
    results (e.g. aarch64 vs armv7), not assumed.

    the daemon and runtime still run resident on the Pi. Real memory footprint
    must be measured on the actual hardware. The 75k-agents-on-a-Pi headline
    measured idle synthetic agents, not inference or live tool workloads.
