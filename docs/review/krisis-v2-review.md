# Krisis spec v2: remaining gaps and proposed v2.1 repairs

Reviewed 2026-09-30. Primary source: [krisis-spec-v2.txt](krisis-spec-v2.txt), which matches the copy in `/home/akarta/Projects/krisis/`. I compared it with the [first review](krisis-review.md), [shared stack contract](STACK_BUILD_CONTRACT.md), the current Kleroterion specification, and the local Dianoia, Hestia and Dokime interfaces. This reviews a draft; Krisis has no implementation or measured result here.

## Assessment

V2 is a substantial improvement. It separates answer selection from Kleroterion's Dianoia action selection, demotes model likelihood from a universal prior to an optional feature, separates agreement from correctness, adds abstention, and defers online/configuration selection. Its first-build boundary is now credible.

The remaining issue is **operational completeness**: the selector cannot yet be implemented consistently because candidate creation, support scoring, missing features, threshold meaning, and runtime perturbations lack a precise contract. Close these before freezing v2 as a build prompt. The strongest first release is a bounded, deterministic selector over a small set of already generated **answer** candidates, with explicit states for unsupported or unavailable verification.

## Recommended v0 contract change

**Input:** `SelectAnswersRequest` with request/trace ID, question class, immutable evidence snapshot, exactly 1–N generated `AnswerCandidate`s, model/generation parameters and digests, cited passage IDs, hard eligibility and rejection reasons, deadline/resource budget, and feature provenance. Kybernetes owns candidate generation; Phylax and source checks produce the hard mask. Dianoia may supply a contradiction signal, but no component may relabel that as grounded support.

**Decision order:**

1. Validate schema, versions, IDs, fixed query/evidence snapshot and budget.
2. Apply non-compensable access, provenance, contradiction and citation-resolution gates.
3. Select one frozen feature profile shared by all remaining candidates. Require the profile's feature availability and calibrated units.
4. Score and rank deterministically; define tie-breaker using stable candidate ID. Apply a separately defined acceptance threshold to a named quantity.
5. Return selected ID or a distinct typed abstention/failure. Kybernetes rechecks the selected candidate against current policy/index before streaming it.

**Output:** selected candidate ID, full ranking, each score component and missingness, active feature profile, threshold and decision reason, model/index/policy versions, incurred total-turn and incremental selection cost, trace ID, and final status. Sensitive text stays out of audit logs by default.

For the first implementation, use a support-and-citation profile **only when claim-level support exists**. Otherwise compare a simple deterministic eligible-candidate baseline and explicit abstention. Add consistency and likelihood as separately ablated, optional profiles after their contracts and calibration are proven. This avoids a complex weighted formula whose primary signal does not yet exist.

## Answers to v2's five questions

1. **Agreement classes:** ship normalized closed-form answers first (number/unit, exact entity/date, canonical choice) with audited equivalence rules. Exclude open-ended multi-claim prose from consistency scoring until claim decomposition and human-audited semantic equivalence are available. Report the excluded share; never count it as stable.
2. **Weight data and freeze owner:** use a versioned Dokime development split disjoint by source/question family from the final test. Krisis maintainers propose weights; the stack owner approves the frozen policy manifest with hash, dataset IDs, scorer versions and guardrails. Dokime recomputes the report. A signature is optional; an immutable recorded approval is required.
3. **Shadow exploration:** set no live propensity floor in a pure shadow phase. It observes the deployed policy's action and can score alternatives only where labels are available independently. If causal online learning is later needed, design a separate, consented, bounded exploration trial with logged propensities and user-facing safeguards; do not smuggle exploration into “shadow.”
4. **Hostile-feature cases:** Dokime should own the frozen suite from day one; Krisis/Kybernetes/Dianoia maintainers contribute attack fixtures, and an independent reviewer labels claim support, citation validity and intended invariances. Keep some attacks held out from feature/weight tuning.
5. **Starting budgets:** avoid claiming measured hardware capacity from a spec. A conservative **configuration to benchmark**, not a performance promise, is at most two answer candidates, zero live perturbation calls, and no extra GPU model call inside Krisis. Allocate a fixed fraction of Kybernetes's remaining deadline and token budget; reject or abstain before overrun. Set concrete wall-time/VRAM limits from a real Hestia baseline on the target 16 GB device, then freeze them in the policy manifest.

## What to change next

Revise the v2 text at sections 4–6 to make it answer-only, define candidate production, support/verification states, feature profiles, threshold semantics and typed failures. Revise sections 8–9 to distinguish build readiness from measured release and shadow scoring from actual exploration. Add a small contract fixture with two candidates: one fluent but unsupported, one supported; one missing-feature case; one stale snapshot; and one all-rejected case. The expected selection or abstention should be unambiguous without a model call.

Once those changes are made, Krisis is ready for an implementation prompt. The existing v2 is a strong direction, but not yet a deterministic production build contract.
