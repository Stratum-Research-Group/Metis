CONTEXT
Dokime is the measurement layer for a local AI stack. It generalizes LTHCM's benchmark discipline: every model, prompt, or pipeline change gets real numbers with confidence intervals, never vibes.

HARD CONSTRAINTS
- Models are queried through the Hestia serving layer API (OpenAI-compatible), never loaded directly. Read hestia's server module and models.yaml in the submodule for the exact route schema (chat completions, streaming, model list endpoint) - do not re-specify the API here; name where to look.
- Every run: fixed seeds, run_id, manifest with per-artifact checksums, hardware line, model identifier. Reproducible from a clean clone.
- Statistics follow the LTHCM convention: point estimates plus paired bootstrap 10k CIs (seed 42), per-query diffs preserved.
- Add the existing stack projects to the workspace as git submodules, pinned to their current commits: LTHCM (https://gitlab.com/akarta-315h/LTHCM @ 8a71605379ee32059e714feb3648cf74f4b42dc6), dianoia (https://gitlab.com/akarta-315h/dianoia @ da7ce83cb05f3b44764fc59ab5c325995c6fd07c), and hestia (https://gitlab.com/akarta-315h/hestia @ edd1bcf411180dd3c9b1171057d03f400b3bfb96). They are read-only dependencies: never modify their contents, never copy their files into this repo's own tree, and never push or upload their contents anywhere.
- Dokime integrates with hestia through its OpenAI-compatible HTTP API only. The hestia submodule exists so the builder can read the real API surface and model registry, never to import hestia code.
- Dianoia is a read-only reference for deliberation and prompt patterns. Dokime's prompt-variant regression compares exist to measure changes to patterns like dianoia's; that is its role in this repo, nothing more.

BUILD, IN THIS ORDER

1. REPO SCAFFOLD
- New repo "dokime", Python 3.12+, src layout, pyproject.toml.
- Dependencies: httpx for the API, numpy allowed for the bootstrap statistics, stdlib otherwise. Nothing else without asking.

2. TASK PLUGIN INTERFACE
- A task = dataset loader + scorer. A task implements a protocol: load() -> list[Query] and score(query, response) -> float. Tasks are discovered via entry points.
- Ship one reference task: ~25 synthetic ARC-style multiple-choice items (synthetic stand-in, no licensing baggage) in a single local JSON file.

3. RUNNER
- Single CLI entry with subcommands: dokime run, dokime compare, dokime tasks.
- dokime tasks lists all discovered tasks with their item counts.
- Run config is a TOML file naming models, tasks, prompt variant, seed, temperature, and max tokens; CLI flags override config values. For example:
  models = ["<served-model-id>"]
  tasks = ["<reference-task-id>"]
  seed = 42
  temperature = 0
- Executes one or more models against one or more tasks as a matrix via the serving API, writing one results JSONL per run. A single dokime run invocation produces one run_id; all model x task combinations are written to that run's JSONL. The seed is sent in the API request itself; temperature defaults to 0. Both are overridable in the run config.
- Per-query results logged to JSONL with fields: run_id, task_id, query_id, model_id, prompt_hash, predicted, expected, score, latency_ms, timestamp. score is a float; prompt_hash is SHA-256 of the rendered prompt text.
- Errors: retry 3 times with exponential backoff. After that, log the query as a null result with the error recorded. Never silently skip a query.
- All artifacts live under runs/{run_id}/: results JSONL, manifest, compare reports.

4. STATS
- Point estimates, paired bootstrap CIs, per-query diff analysis between two runs of the same model (including prompt changes) in ordinary compare; between two models only in explicit within-run cross-model compare.

5. MANIFEST + REGRESSION COMPARE
- Manifest writer: a JSON file with run_id, checksums over the results JSONL and each task dataset file (keyed by task ID), the repo's git sha, hardware, model ids, seed, and max_tokens. All file checksums are SHA-256 over the raw file bytes. The manifest is auto-written by dokime run; there is no standalone regenerate subcommand in v1.
- Hardware captured via the platform module, plus nvidia-smi output when present.
- Compare command: diff two runs and flag changes whose CI excludes zero. Compare takes a --model <id> flag to scope pairing within a run, plus an optional --task <id> to slice further. If a run contains multiple models and --model is absent, compare exits non-zero and lists the models present; it never pairs results across models.
- Explicit cross-model mode: dokime compare <run_id> --cross-model <model_a> <model_b> --task <task_id>. This mode compares the two model IDs within that single matrix run only, pairing by query_id for the same task, rendered prompts, and seed. It is distinct from ordinary two-run --model compare; --cross-model cannot be combined with a second run ID or --model. Require results for both models and that task in the run; refuse with a non-zero exit and clear message if either is absent, the two models' query_id sets (including logged failure rows) differ, or their recorded dataset checksums for that task differ. Check matching prompt hashes per query and the run seed before pairing, refusing mismatches. Exclude failure/null-result rows from paired statistics and report each model's failure count separately, consistent with the runner's error-row rules. On remaining complete pairs, use paired bootstrap with 10,000 resamples and fixed seed 42, preserve per-query diffs, and flag changes whose CI excludes zero. Write each report under runs/{run_id}/ to a distinct path containing collision-resistant filesystem-safe encodings of both model IDs and the task ID; do not overwrite reports for another model pair or task. Ordinary two-run --model compare remains same-model only and never pairs across model IDs.

6. TESTS
- pytest.
- Stats module: unit tests with known-answer fixtures.
- Runner: integration tests against a mock OpenAI-compatible server.

OUT OF SCOPE
- Hosted eval APIs, human evaluation, leaderboard features.

DEMO
- Query hestia's model-list endpoint and use whatever model is currently served - do not assume an 8B.
- Run the reference task on that model, produce run_id + manifest + CIs, then run a second prompt variant and show the regression compare output.
