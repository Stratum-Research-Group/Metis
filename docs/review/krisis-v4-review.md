# Krisis v4 review request: gaps in the proposed repairs

Reviewed 2026-09-30. Source: [krisis-v4-review-request.txt](krisis-v4-review-request.txt), read alongside [the v3 review](krisis-v3-review.md) and [v3 spec](krisis-spec-v3.txt). The request describes what **v4 will say**; it is not the v4 specification or a policy manifest. The copy in `/home/akarta/Projects/krisis/` matches. Findings below assess the proposed changes, not implemented behavior or measured quality.

## Assessment

The proposed v4 addresses nearly all round-3 issues in the right direction. The two-track release, grounded hard rejections, worked policy manifest, same-candidate-set evaluation, complete outcomes, and replay distinction would make Krisis much easier to build and audit.

The largest remaining risk is now the **evidence verifier**. A “supported” verdict means a claim is supported by a cited span under a measured verifier; it does not prove the source is true. A false-support rate measured on one frozen test cannot by itself guarantee safe behavior after a model, corpus, or query distribution changes. The v4 spec needs an exact reliability and fallback contract before making grounded selection the production path.

## Remaining issues and concrete repairs

| P0 | Item 4: verifier audit “before every manifest freeze,” agreed error bounds, automatic deactivation. | No primary verifier metric, denominator, confidence bound, minimum sample, per-domain slice, trigger owner, post-release drift response, or recovery rule is named. Auditing a verifier built near candidate generation does not make errors independent. | Define versioned claim-level labels and a **false-support upper confidence bound** at a frozen operating point, minimum audited cases and critical slices, source/corpus shift checks, and a Kybernetes-owned activation switch. A bad or unavailable verifier disables grounded profiles and returns a typed status; reactivation requires a new passing Dokime bundle. Test trigger, rollback and stale audit artifacts. |
| P0 | Item 4: verdicts “can only be abstained from, never overridden.” | A mistaken verdict needs correction, but a live caller must not simply flip it to `supported`. | Permit evidence correction or human adjudication as a **new versioned verification run**, with provenance and approval, rather than mutating a verdict in place. Kybernetes may abstain or retry under a bounded policy; Krisis cannot override the original result. |
| P0 | Item 5: unclassified/ambiguous queries get a conservative “eligibility + support only” default. | If support verification is unavailable, this default has no usable support feature. Classifier confidence can also be poorly calibrated; a high-impact misroute can activate a weaker profile. | Default profile must state `requires_grounding`, verifier-unavailable behavior, and a deterministic abstain branch. Use calibrated confidence/ambiguity thresholds; for multi-class matches choose the **most restrictive** applicable requirements or abstain, never merely the first rule if it is weaker. Include a canonical manifest and JSON inputs/outputs that two implementations can replay byte-for-byte. |
| P0 | Item 6 compares selection arms on identical candidate sets and the whole n=2 pipeline with n=1. | It does not explicitly say all selector arms share the same hard authorization, provenance, contradiction and support gates. A likelihood-only arm with weaker gates is an invalid comparison. | Freeze one candidate/evidence set and one hard eligibility mask for all **selection ablations**; vary only the named ranking feature. Report a second, end-to-end n=2 vs n=1 comparison with all generation and verification cost/failures. Separate attribution in the report. |
| P1 | Item 7 adds a complete outcome enum and mixed-reason precedence. | A single value may hide partial generation failure or several rejection reasons. `SCHEMA_INVALID`, `UPSTREAM_GENERATION_FAILED` and `CANCELLED` are operational errors rather than normal selection outcomes. | Use a top-level `status` (`selected`, `abstained`, `failed`, `cancelled`) plus a typed `reason`, per-candidate rejection list, and upstream-attempt counts. Define precedence only for a single aggregate reason; never discard secondary causes. Test partial upstream failure where one valid candidate remains. |
| P1 | Item 8 proposes near-duplicate merging that preserves negation/numbers/citations. | “Near duplicate” is not deterministic without a semantic policy, and subtle modality, scope, entity or temporal changes can reverse an answer. | In v0, deduplicate only exact normalized text **and identical citation IDs/snapshot**. Preserve lineage. Add semantic dedup later with a validated equivalence model and adversarial pairs beyond negation: units, dates, quantifiers, entities and negated clauses. |
| P1 | Item 9 says a redacted log supports decision replay, with immutable artifacts for recomputation. | Exact feature values, IDs and rejection reasons can still reveal private content. “Immutable” conflicts with deletion/retention obligations if raw user queries are retained indefinitely. | Define field-level sensitivity labels and retention periods. Store hashes and encrypted/restricted artifacts where needed; log enough to replay policy arithmetic while making feature recomputation conditional on permitted artifact retention. Document what becomes non-recomputable after deletion. Test redaction and authorized replay. |

If exposed to users, compare its failure/abstention behavior against the current Kybernetes path; never call it an answer-quality improvement. |

## Suggested wording for the critical verifier rule

> A grounded profile may select an answer only when every factual claim has a versioned `supported` verdict against its exact cited passage and snapshot. `Unsupported`, `contradicted`, `unverified`, verifier outage, and stale citations cannot be converted to support by likelihood or consistency. The verifier's support precision and coverage are measured on independent, human-audited held-out data with a preregistered bound and slice gates. If the current verifier version or corpus is outside the validated envelope, Kybernetes deactivates grounded selection and returns an explicit unavailable/abstain state. A corrected verdict is a new auditable verification run, not an in-place override.

This is a **source-grounding** contract. It does not certify that the cited source itself is true; source trust and contradictory-source handling require separate labels and evaluation.

## Checks to run when the actual v4 spec arrives

1. Recompute every numeric fixture from the manifest, including `score == tau`, missing features, multi-class routing and mixed rejection reasons. A second implementation should get the same bytes for the policy decision.
2. Show that Foundation can release without a gain claim while Selector Promotion remains disabled until Dokime's held-out gate passes.
3. Verify `requires_grounding=true` plus verifier outage, stale audit, or unknown class **never** yields a response labeled grounded.
4. Verify each selector ablation uses the same candidate set and hard mask. Report the separate end-to-end n=2 versus n=1 cost and quality.
5. Demonstrate fail-closed deactivation, reactivation and replay after a verifier-version change; test the declared artifact-retention limits.

The request is a strong revision plan. The actual v4 document should become the build contract only after these choices appear as schemas, numeric manifest entries, deterministic fixtures and measured release gates. No v4 performance or production claim is established by the request alone.
