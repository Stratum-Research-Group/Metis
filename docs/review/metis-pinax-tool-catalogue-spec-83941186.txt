METIS TOOL CATALOGUE + LARGE TOOL INVENTORY
Proposed working name: "pinax" (ancient Greek for tablet, list, register,
catalogue). Name proposed only, not selected. A name carries no safety
guarantee; the design below is what does or does not protect you.
Status: design proposal for Nick. No code written, nothing installed, no repo
changes. Date: 2026-10-17. Metis context @ 369939e (round 4 review facts).
Machine context assumed: Omarchy (Arch-based) Linux, Hyprland, RTX 5060 Ti.
Nothing in the inventory is claimed to be installed on your machine; the
passive scanner in section 4 establishes what actually exists.
Sources for CLI behaviour claims: appendix A (official docs, checked
2026-10-17). Flag-level details describe upstream behaviour of the named
tool family; the exact flags of YOUR installed version must be confirmed
against the local man page the catalogue records, since versions differ.

=====================================================================
0. WHAT YOU ASKED, ANSWERED DIRECTLY
=====================================================================

Yes, there should be a DB. A local SQLite catalogue that records, per tool:

  - what it is called and what it does (one line)
  - where each installed copy lives: invocation path, resolved target,
    and env/venv identity (several copies may coexist and differ)
  - where its manual lives (man page location, help text, upstream docs)
  - how it is invoked (arguments, or a structured signature for curated tools)
  - what kind of thing it can do (read, write, network, destructive, exec)
  - whether it is actually installed right now, on which machine, and when
    that was last checked
  - where each fact came from (PATH scan, pacman, man-db, hand-written entry)

The model then asks the catalogue instead of relying on training memory.
That REDUCES (does not eliminate) three real risks: hallucinated flags,
wrong assumptions about what is installed, and missing documentation. Only
running the tool under the gate reduces the rest.

Three things the DB is NOT:

  1. It is not permission. The catalogue documents; Phylax authorizes, and
     the execution environment enforces. A low risk tier in a row must never
     be the only thing between the model and a destructive command.
  2. It is not an installer. "not installed, package name X" is information;
     installing is a gated action like any other.
  3. It is not authority for new tools. A tool appearing on the machine is
     catalogued as unvetted and stays denied until you curate it.

catalogue makes those problems more important, not less. This feature
lands AFTER or ALONGSIDE those fixes, never as a substitute. A DB row
cannot contain a bad command; only isolation does (section 5).

=====================================================================
2. DATABASE SCHEMA (SQLite, single file, e.g. pinax.db)
=====================================================================

SQLite fits: one file, zero services, already the Metis convention for
local structured state. FTS5 for search is a COMPILE OPTION, not
guaranteed (sqlite.org compile docs, appendix A): check for it at build
time and fall back to LIKE search if absent.

Key design decisions, driven by how machines actually look:

  - Rows are per (machine, invocation path), not per tool name. Your
    system python3 and a venv python3 are different rows: two venvs can
    point at the same resolved python binary yet behave completely
    differently, and "yq" can be two unrelated programs (see 3.2).
    tools.name is a label; identity is host + invocation path +
    resolved target + env identity.
  - Interpreter/shell context is recorded: shebang of scripts, owning
    venv, shell for builtins. What runs depends on it.
  - entry_kind separates INSTALLED facts from CANDIDATES (section 3 is a
    wanted list). Candidate rows carry package names so "what would I
    install" is answerable without pretending it exists.
  - Freshness is per row and checked at USE time: before dispatching
    a curated binary, kybernetes re-stats the path and re-hashes it
    against the row. This NARROWS the scan-now-run-later (TOCTOU)
    window; it does not close it - a replacement can land after the
    hash, and identity is more than one file (interpreter, linked
    libraries, config). Where the risk warrants it, dispatch anchors
    harder: an immutable trusted snapshot of the executable plus its
    dependency/config set, or execution bound to an already-open,
    already-verified file descriptor (e.g. execveat on that fd) so the
    checked bytes are the executed bytes - with section-5 isolation as
    the independent backstop either way.
  - pacman ground truth is partial ground truth: pacman knows packaged
    files only. Ad-hoc installs (curl-sh scripts, cargo, manual copies)
    appear in the PATH scan with package "unknown". Both signals are
    kept, neither is trusted alone.

  tools(
    id,
    host_id,               -- which machine/environment this row describes
    name,                  -- canonical label, e.g. "curl"; NOT unique
    kind,                  -- binary | script | builtin | structured
    entry_kind,            -- installed | candidate
    summary,               -- one line, curated or from --help
    invocation_path,       -- path as invoked, e.g. .venv/bin/python
                           -- (may be a symlink; same target + different
                           -- venv = different behaviour)
    resolved_path,         -- resolved absolute target, or NULL for candidates
    env_identity,          -- owning venv/env root that changes behaviour
    interpreter,           -- shebang/shell context where applicable
    sha256,                -- of the executable, for use-time re-verify
    version,               -- from package metadata or vetted probe, or NULL
    package,               -- owning package, or "unknown"
    package_manager,       -- pacman | pip | cargo | manual | unknown
    install_state,         -- installed | not-installed | broken | unknown
    risk_tier,             -- T0 | T1 | T2 | T3  (see section 5)
    discovered_by,         -- path-scan | pacman | man-db | curated | manual
    first_seen, last_verified,
    notes
  )

  tool_docs(
    tool_id REFERENCES tools(id),
                           -- every doc row is persistently bound to one
                           -- tool row
    doc_kind,                -- man | help | info | upstream-url | example
    locator,                 -- man file path+section, file path, or URL
    version_scope,           -- which tool version this doc describes;
                             -- local man pages match the installed version
    sha256, size_bytes,      -- changed docs are detectable
    fetched_at
  )

  tool_capabilities(
    tool_id, capability,     -- file-read | file-write | network-read |
                             -- network-write | process-exec | destructive |
                             -- privilege | install | interactive
    detail                   -- e.g. "uploads via -T/--upload-file"
  )

  tool_risk_overrides(       -- curated per-pattern escalations
    tool_id, pattern_kind,   -- subcommand | flag | regex
    pattern,                 -- e.g. "push", "--upload-file", "--delete"
    tier,                    -- tier this pattern forces
    note
  )

  tool_signatures(           -- structured invocation for curated tools
    tool_id, call_name,      -- e.g. "http_request" wrapping curl
    arg_schema_json,         -- JSON schema of accepted arguments
    curated_by, curated_at
  )

  scan_runs(                 -- audit trail of discovery runs
    id, host_id, started_at, finished_at, scanner_version,
    added, removed, changed
  )

Referential integrity: tool_docs, tool_capabilities,
tool_risk_overrides and tool_signatures all declare
FOREIGN KEY (tool_id) REFERENCES tools(id). A doc, capability, override
or signature row cannot exist without its tool row.

=====================================================================
4. DISCOVERY: PASSIVE FIRST, PROBES ONLY IN ISOLATION
=====================================================================

Design rule: the scanner must be safe to run against a hostile PATH. An
executable that nobody has vetted must NEVER be executed by discovery -
a timeout is not a sandbox, and malicious code can do anything it wants
in its first millisecond. Discovery is therefore two tiers:

PASSIVE (default). The only programs run are trusted metadata utilities
(/usr/bin/pacman, /usr/bin/man, ...), invoked by ABSOLUTE path in a
sanitized environment so a hostile PATH cannot hijack them. No DISCOVERED
TARGET is ever executed - an unvetted binary from PATH is only ever
listed, never run:

  1. PATH walk: list executable names and resolved absolute paths from
     $PATH directories, plus stat metadata (owner, mode, mtime, symlink
     target). Pure readdir/stat.
  2. Package metadata: pacman -Q lists installed packages; pacman -Qo
     <path> maps an executable to its owning package; pacman -Qi gives
     the version. All from the package database, no execution. (Assumes
     Arch/Omarchy; verify distro at scan time, record package_manager.)
     pacman knows packaged files only - ad-hoc installs show up in the
     PATH walk with package "unknown".
  3. man-db files: resolve page FILES via manpath/man -w and record
     locator + sha256 + size. Do not render man pages in the scanner:
     rendering runs a groff pipeline and a pager (man(1), less(1)),
     i.e. executes helpers on untrusted input. Text extraction from the
     raw roff source happens only in the isolated pipeline below.
  4. Curated seed file (versioned in the repo): summaries, capabilities,
     tiers, overrides, signatures for section 3 plus the structured
     kybernetes tools. Discovery fills paths/versions; curation fills
     meaning and risk.
  5. Manual entry: pinax add <name> for aliases, functions, remote-only
     tools.

ACTIVE PROBES (only for curated, allowlisted tools, only in isolation):

  - --version / --help output for tools you have already curated, run
    inside an isolated environment: no network, empty credential-free
    environment (explicit env allowlist), hard time cap, output size
    cap, whole process-tree kill on expiry. A container (podman) is the
    natural fit; a bare "timeout 5 tool --version" is NOT acceptable.
  - Doc text extraction (roff -> text, or --help capture) runs in the
    same isolated environment, output hashed and size-capped.

Rescan: on demand (pinax scan) plus an optional pacman hook so installs
update the DB. Staleness is first-class: rows older than N days report
as stale; "stale" never answers as "installed" without a rescan.
Uninstalled tools are marked not-installed, never silently deleted.
Discovery never installs anything and never authorizes anything: a newly
appearing tool is catalogued as unvetted and default-denied until
curated.

ACCEPTANCE TESTS for the scanner (run in a throwaway VM/container, not
on your real home directory):

  A1 malicious-PATH: a directory on PATH contains an executable that
     writes a marker file and phones out if executed. After a full
     passive scan, the marker must not exist.
  A2 symlink swap: a curated binary's path is replaced by a symlink to
     something else between scan and dispatch. The dispatcher's
     use-time re-check (section 2) must detect the change and refuse
     to run it.
  A3 hanging helper: a curated probe target that never exits. The probe
     harness must kill the whole process tree within the cap and mark
     the row broken.
  A4 help-text exfiltration: a probe target whose --help output embeds
     content that would be dangerous if obeyed, and which attempts
     network egress. The probe environment has no network and no
     credentials; the output lands in the DB as inert, capped text.
  A5 unvetted newcomer: a brand-new binary appears on PATH. It is
     catalogued, marked unvetted, and any attempt to dispatch it is
     denied.

=====================================================================
5. RISK TIERS AND THE ISOLATION MODEL (Phylax consumes)
=====================================================================

  T0  Read-only, local, no secrets. Default allow inside scoped roots.
  T1  Local writes scoped to allowed roots. Path validation mandatory.
  T2  Network read, allowlisted destinations, size/redirect caps, no
      local-network targets.
  T3  Irreversible, egress-capable, privileged, system-mutating, or any
      execution of untrusted code/config. Explicit approval, every time,
      with the exact command shown.

Five corrections to naive versions of this table:

  1. Tier attaches to an INVOCATION, parsed, not to a binary. The same
     curl is T2 for a GET and T3 for an upload; the same git is T0 for
     diff and T3 for push. tool_risk_overrides encodes the patterns that
     force escalation, matched on parsed arguments, never substring
     search (round 4 flagged Phylax destination-substring matching:
     substrings are how "allow example.com" becomes
     "curl evil.com?next=example.com").

  2. Many "safe" tools have an execution surface (appendix A sources):
     awk has system(); GNU sed has the e command; find has -exec and
     -delete; rg has --pre and a config file; jq loads modules; less
     runs shell escapes; sqlite3 dot-commands include .shell and .load;
     git runs hooks, aliases, external pagers/diff drivers; make/cargo/
     npm run code from the project; gcc/clang load plugins; tar and
     ImageMagick have format-level traps. Consequence: the tier table
     describes each tool's common form, and any GENERATED or UNTRUSTED
     script/config/input for these tools is itself code and escalates.

  3. No parser of arbitrary shell can enforce policy alone. Compound
     commands, pipes, redirections, command substitution, interpreter
     -c flags, environment, cwd, config files and hooks all change what
     runs. Therefore sandboxed_bash must (a) fail closed on anything it
     cannot parse into a known-safe form, and (b) rely on boundaries the
     OS enforces independently of parsing: a filesystem allowlist (bind
     mounts/namespace), a network egress allowlist (firewall/proxy),
     and a credential-free environment. Parsing decides intent;
     isolation limits damage when parsing is wrong.

  4. Reads and GETs leak too. T0 reads can expose secrets
     (cat ~/.ssh/..., env output) - contained by the filesystem boundary
     and output filtering, not the tier. T2 GETs carry data in query
     strings and headers, follow redirects, resolve DNS, and can target
     localhost/link-local (SSRF). Fetched content that is then executed
     (curl | sh) is T3 by construction: gate any pipe into an
     interpreter.

  5. Discovery never authorizes (repeated from section 4 because it is
     the cheapest place to get it wrong): unvetted = deny.

=====================================================================
6. TRUST MODEL: WHY TIERS CANNOT LIVE ONLY IN THE DB
=====================================================================

If rm's tier were only a mutable row, anything that can write the DB
could downgrade rm to T0. So:

  - Curated tiers and overrides ship in the seed file, versioned in the
    repo, loaded at scan time. DB rows for discovered-only tools default
    to the most conservative plausible tier until curated.
  - Phylax treats the catalogue as ADVISORY data. Deny-by-default stays
    in policy code. Catalogue compromise must be able to hide a tool,
    never to un-gate one.
  - Doc text (man pages, --help, README scrapes) is UNTRUSTED DATA:
    quoted into the model's context size-capped, never executed, never
    obeyed. A man page saying "run X with sudo" is text about X. Same
    injection class as untrusted email/web content; label doc excerpts
    as data in prompt assembly.
  - scan_runs plus per-row sha256 give an audit trail: a changed binary,
    a changed man page, or a new path is visible, and the use-time
    re-hash (section 2) refuses stale approvals.

=====================================================================
7. RETRIEVAL: HOW THE MODEL USES IT WITHOUT DROWNING
=====================================================================

The failure mode to design against: stuffing ~200 tools and their
manuals into the prompt. The catalogue exists so the model can ask, not
memorize.

  Level 0 - digest. Compact list: name, 5-10 word summary, tier, grouped
    by category. Usually only the relevant categories are shown,
    selected by the orchestrator from the task.
  Level 1 - signature. For the chosen tool: the curated argument schema
    (tool_signatures) or the invocation synopsis from its LOCAL docs
    (which match the installed version, unlike upstream URLs).
  Level 2 - doc slice. On demand: the relevant local man section or
    --help excerpt, size-capped (~2-4KB), labeled as untrusted
    reference text.
  Search - full-text over names, summaries and help text (FTS5 if the
    SQLite build has it - verify, it is a compile option - else LIKE
    fallback): "extract audio from a video" should return ffmpeg.
    kybernetes exposes catalogue_lookup and catalogue_docs as two small
    structured tools.
  Unknowns - a tool absent from the catalogue is reported as unknown,
    and unknown means "ask or use a known equivalent," never "improvise
    flags from memory."

LTHCM can later store learned usage ("this project builds with just") on
top; the catalogue remains the live fact source for existence and
location.

=====================================================================
8. EVALUATION (dokime, small and honest)
=====================================================================

  - Lookup correctness: 50 "which tool does X" questions with known
    answers; top-1 and top-3 retrieval accuracy.
  - Inventory accuracy: scanner report vs pacman -Q on the real machine,
    reported as false-installed / false-missing counts, with the known
    gap stated (pacman misses ad-hoc installs; PATH scan misses
    unlinked packages).
  - Scanner safety: acceptance tests A1-A5 from section 4, in a
    throwaway environment.
  - Tier spot checks: curated tier assignments reviewed by you, not
    asserted by the system.
  - No synthetic-pass shortcuts: if the machine lacks the tool, the eval
    says SKIP, not PASS (round 4 flagged this failure class elsewhere).

=====================================================================
9. BUILD PHASES (you build; this is the spec)
=====================================================================

  P1  Schema + passive scanner (PATH walk, pacman metadata, man-db file
      locators) producing pinax.db plus a scan report. Executes nothing
      from the machine.
  P2  Curated seed for the section-3 inventory + use-time re-hash in
      dispatch + catalogue_lookup/catalogue_docs in kybernetes.
  P3  Isolated probe harness for curated --version/--help/doc
      extraction; retrieval levels 0-2 wired into the coding agent loop;
      doc-injection labeling.
  P4  Prosopon read-only catalogue browser; dokime evals incl. A1-A5;
      optional pacman rescan hook.

Explicit non-goals for v1: installing tools, executing tools through the
catalogue (kybernetes dispatch already does that), auto-authoring
signatures from man pages (too unreliable to trust unreviewed), and any
Apply/write path in the dashboard.
