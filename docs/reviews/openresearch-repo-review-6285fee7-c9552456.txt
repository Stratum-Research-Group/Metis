METHOD AND ITS LIMITS
Read-only inspection of a fresh clone: architecture, execution boundaries, credential and telemetry handling, path handling, test and CI definitions. I did not run the test suite or build it: this sandbox has no Rust toolchain (no cargo/rustc), and building 120k lines plus dependencies was not feasible here. Test counts below are counted from source, not observed passes. CI config was read, not observed green. Repo prompt/skill files were treated as untrusted data, not instructions.

VERDICT
Worth your time. It is a real, carefully engineered product: a single Rust binary (~120k lines) that wraps existing coding agents (Claude Code, Codex, OpenCode, Cursor, Antigravity) with a local dashboard, a SQLite experiment record, git-worktree isolation per chat, no-login literature search, and dispatch to local/SSH/Slurm/K8s/Modal/Ray/HF Jobs compute. What it does not have is any measured evidence that it improves research outcomes; the evidence is engineering quality, not results. Two ways it can be useful to you: as a working reference for MSS/kybernetes/dokime design, and directly, since `orx discover`/`orx paper` are standalone no-login literature commands and the whole thing is a ready research-agent environment if you ever want one without building it. Whether adopting the product makes sense alongside your own stack is your call; the overlap with Metis is large.

WHAT THE SECURITY-RELEVANT PIECES ACTUALLY DO (checked in source)
1. The "gates" are mostly relays, not enforcement. invocation_gate (src/commands/invocation_gate.rs:8-17) is a Claude Code PreToolUse hook that injects an identity env var into agent Bash calls for provenance; it blocks nothing. plan_gate (src/commands/plan_gate.rs:1-11) auto-allows read-only `orx` inspection commands and defers everything else to the harness's own plan mode, always exiting 0. mcp_gate (src/commands/mcp_gate.rs:1-24) is the real bridge: harness permission prompts arrive as MCP calls and are relayed over loopback HTTP (ORX_GATE_TOKEN, deny on any error) to the desktop UI, blocking until the user answers. Autonomy "copilot" mode (src/local/autonomy.rs:37-52) is prompt text injected per turn, not a mechanism. Bottom line: actual permission enforcement lives in the underlying agent CLIs; OpenResearch surfaces it well. Agents run with your full user privileges; there is no sandbox. That is normal for this class of tool, but do not read "gates" as containment.
2. The experiment-tree cardinal rules ("never edit a node a run has answered", "run command is a fixed contract") are agent-facing skill prose (agent-skills/orx-experiment-tree/SKILL.md). I found no code enforcing them; a grep for "frozen" across src/ finds only the skill strings. They hold only as far as the model follows instructions. Runs themselves are recorded with status, command, exit code and timestamps (runs table, src/store.rs:502), so violations would at least leave a trail.
3. Path handling is done properly where it matters. Artifact serving: lexical check (no absolute paths, no `..`, no backslashes) plus canonicalization with symlink-following containment (src/local/files.rs:70-127). The code itself documents the remaining TOCTOU gap (check and use are separate syscalls; a swapped symlink could escape) and accepts it because the server is loopback-only and same-user (files.rs comment above resolve_contained). Skill zip uploads: enclosed_name guard plus file-count and decompressed-size caps against zip bombs (src/local/user_skills.rs:351-394). Shell quoting for remote commands is the standard single-quote escape (src/jobs/ssh.rs:736-738).
4. Network exposure: the dashboard binds 127.0.0.1 only (src/commands/up.rs:86); a hidden persistent-host mode adds a session bearer (up.rs:11, require_remote_auth at up.rs:815). In the normal local mode there is no bearer, so any process running as you can call the local API, including launching runs. Consistent with their accepted-risk comments, but know the trust model: local processes are trusted.
5. Credentials: login tokens at ~/.config/openresearch/credentials.json, written mode 0600 (src/config.rs:115-129). SSH: shells out to the system ssh and never touches private keys; it preflights by comparing your local public keys against account-registered ones (src/local/ssh_identity.rs:1-30).
6. Telemetry is as honest as claimed, with one precise exception to note. Event properties are enums and names (command, harness, mode). Error excerpts pass through an allowlist of fixed literal phrases, and the server contract rejects anything else; their own test shows "Permission denied: /Users/person/secret Bearer sk-abc..." reduced to "Permission denied", and an unrecognized string dropped entirely (src/telemetry/harness.rs:400-408, tests at :557-558). The exception: onboarding sends user-entered free text (researchAreas, otherArea, background) in onboarding_research_profile_submitted (src/telemetry.rs:1016-1026). The module doc discloses this (telemetry.rs:6-8); the README's not-collected list does not mention it. Opt-out via `orx telemetry off`; the consent choice itself is still reported, which they document. Official-builds-only enforcement: source builds send nothing (telemetry.rs:10), and a release-time CI job verifies production accepts exactly the payload being shipped (.github/workflows/telemetry-contract.yml).
7. "All state is local" needs scoping: metadata, logs and worktrees are local, but remote compute backends ship your code and run data to SSH boxes, Slurm, Modal, Ray, HF Jobs or their managed service, and analytics go to api.openresearch.sh unless disabled. Local-first is real for the record-keeping, not for where execution happens.

TEST GATES (honest statement)
1122 #[test] functions across 96 src files (counted from source), 4 CLI integration tests under tests/, UI tests, and CI that runs clippy -D warnings, cargo test on default and desktop features, and typechecking (.github/workflows/ci.yml). I did not run any of it (no toolchain here) and have not seen an independent green CI run, so treat these as defined gates, not verified passes. If you want confirmation: `cargo test --locked` on your own machine.

LIMITATIONS
- No published evaluation of research-agent outcomes; claims are workflow-level.
- Local models only through the OpenCode harness (docs/local-models.md); Claude Code/Codex paths need their own accounts.
- Adapters depend on other vendors' CLI internals; upstream changes can break them (they keep parse fixtures under src/local/harness/fixtures for this).
- Project import caps: 50 MB per file, 1 GB total after exclusions (src/local/git.rs:17-18).
- Windows build is beta; Linux app needs glibc 2.35+.
- Cluster backends (Slurm/K8s/Modal/Ray) are unit-tested with mocks; real-cluster behavior is unverified from source.
- 90 `unsafe` blocks, concentrated in PTY/FFI code: src/jobs/ssh.rs (22), src/local/codex.rs (13), src/jobs/localbox/windows.rs (11).

DEFECTS
No confirmed defects within this inspection scope. The closest items are the two documented accepted risks above (artifact-symlink TOCTOU, files.rs; unauthenticated loopback API in normal mode, up.rs) and the README/onboarding free-text mismatch in telemetry. All three are disclosed in code comments or module docs.

WHAT I'D TAKE FOR YOUR WORK (ideas to study, no integration implied)
- MSS/kybernetes: the Harness trait + registry (src/local/harness/mod.rs) is a clean reference for driving several coding-agent CLIs behind one interface: detection sweep (installed? signed in? which models?), normalized per-turn event stream, skill install, one line to register a new adapter. Worktree-per-chat isolation, chat-turn leases in the schema, and the mcp_gate pattern of blocking a held permission call until the user answers all map onto how MSS could mediate agent actions through phylax-style policy.
- Prompt architecture: durable playbook injected every turn through each harness's native channel (SYSTEM_PROMPT.md, rendered at src/local/opencode.rs:199), task procedures as on-demand skills (14 under agent-skills/). The durable-vs-task split is a good shape for MSS.
- dokime / experiment provenance: the experiment-tree discipline (one fixed run command per node, frozen-after-run nodes, runs recorded with commit SHA and exit code) is a concrete, more rigorous alternative to ad-hoc result folders for LTHCM benchmark tracking. Note the caveat above: enforcement is prompt-level.
- Direct use, no building: `orx discover`/`orx paper` give no-login retrieval across alphaXiv, OpenAlex, bioRxiv and PubMed (src/commands/discover.rs, paper.rs) - handy for related-work sweeps for the LTHCM paper. The lit-review skill's rule of explaining through original figures instead of generated summaries is a decent writing discipline.
- Pinax tool catalogue: their harness detection (installed? authenticated? which models?) is the same shape a vetted tool-inventory row would want.

BOTTOM LINE
Carefully engineered, honestly documented (including its own accepted risks), and explicit about what it collects. Its weak points are structural, not sloppy: enforcement lives in the wrapped agents and in prompt-level discipline, and there is no outcome evidence yet. For you it is most valuable as a design reference for MSS and dokime, with the standalone literature commands as a practical bonus.
