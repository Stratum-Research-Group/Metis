# Krisis spec v3: remaining build-contract issues

Reviewed 2026-09-30. Source: [krisis-spec-v3.txt](krisis-spec-v3.txt), compared with [the v2 review](krisis-v2-review.md) and the local Dianoia/Hestia/Dokime interfaces. The copy in `/home/akarta/Projects/krisis/` matches this spec. This is a document review, not an implementation or benchmark result.

## Verdict

V3 closes most v2 gaps. It now has an answer-only v0, candidate-generation ownership, typed verifier states, decision-wide feature profiles, a cost boundary, separate shadow and exploration phases, and useful contract fixtures. The remaining problems are a handful of **internal contradictions and missing executable policy details**. Resolve the P0 items below before treating the text as a deterministic first-build prompt. A small eligibility/audit release can be built sooner, but it must have a different release claim from a measured answer-quality improvement.

## Concrete v3.1 decision semantics

1. Kybernetes supplies one immutable answer-candidate set and a request flag such as `requires_grounding`, plus the exact model, prompt/evidence snapshot, generation attempts and failures. One candidate still receives all hard checks.
2. Validate schema and all stable IDs. For grounded requests, reject unresolved citations, unsupported or contradicted claims, stale evidence and forbidden sources before scoring. Treat `unverified` and `verifier_unavailable` as non-grounded states, never as zero contradiction.
3. Select one policy profile for the entire decision from a frozen mapping of question class and available capabilities. The manifest defines exact feature transformations, score equation, calibration, missing-value branch, `tau`, equality, tie order and budget.
4. Rank eligible candidates; apply the profile-specific acceptance threshold. Return a typed status and complete per-candidate reasons. Kybernetes rechecks policy/index before any response is streamed; stale results trigger one bounded rebuild or abstention.
5. Use Dokime to test the same candidate sets under eligibility-only, likelihood-only where available, support-only, and the full profile. Measure the separate n=2 pipeline cost against the n=1 direct path. Keep the foundation release and selector-promotion verdicts separate.

## Proposed resolution of the remaining open questions

- **Support verifier home:** Kybernetes owns the public `verify_answer_claims(answer, cited_spans, snapshot)` contract. A shared library may implement it; Dianoia can call the same interface later. The verifier is separately versioned and evaluated. Krisis consumes verdicts, not raw passage instructions.
- **Development split:** define a new versioned Dokime Krisis suite. Partition by source/document family and query template or event cluster before weight tuning; keep the final test untouched and use only its predeclared release report. Existing 25-item synthetic smoke data is unsuitable for weights.
- **Wall-time/VRAM:** keep the stated two-candidate/zero-live-perturbation starting profile, but make the first Hestia hardware baseline a release prerequisite for absolute limits. Record both cold and warm p95, total candidate-generation time, peak VRAM and failed generations.
- **Threshold equality:** choose `score >= tau` as pass, then freeze it in the manifest and numeric fixtures. This is a convention, not a measured quality claim.
- **Equivalence auditing:** for number/unit, entity/date and canonical-choice classes, write normalization rules and a stratified human audit set with examples of meaning-changing differences. Set the sample size and acceptable disagreement from a pilot/error target before final evaluation; do not invent an accuracy guarantee in the spec.

## Suggested next edit

The v3 text needs a short **policy manifest example** and revised fixtures A, D, E and F more than another broad architecture rewrite. Include numeric candidate features and a threshold so the outputs are mechanically decidable. Add separate Foundation Release and Selector Promotion gates, plus the same-candidate-set evaluation arm. With those changes, the document can be a strong first-build prompt. It still does not establish that the resulting selector improves answer quality until the held-out evaluation is run.
